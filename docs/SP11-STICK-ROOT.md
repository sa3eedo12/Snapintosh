# SP11 root carry: Apple's BaseSystem root as the guest's RAM disk, host side

Status: EXPERIMENTAL; host tests, and one run on the unit, boot 28 (M1 rung 9, 2026-11-20; OBSERVED, one unit, one boot, one stick; section 10). Nothing here authorises a run: every run needs a record of its own that the operator approves by its SHA-256. Labels are those of [SP11-STICK-BUNDLE.md](SP11-STICK-BUNDLE.md): VERIFIED (read in a tree, or shown by a host test that ran), OBSERVED, INFERRED, EXPERIMENTAL, UNIMPLEMENTED, UNKNOWN. The design is `files/baseboot-design-2.md` section A2 (design D-A: keep the five files, carry the root as chunks of GUEST.DAT); the runner half is q1n1's `docs/SP11-PAYLOAD-BIGFILE.md` (`Q1N1_SP11_BIGFILE`, W4).

## 2. Facts (VERIFIED by reading, unless labelled)

- Every size, offset and destination of the interface is `uint64_t` (`probes/sp11-stick-bundle.h`: the chunk and head structures; no `size_t` is used); the hash is q1n1's `q1n1_sha256(const void *, size_t, ...)` with a 64-bit byte count (`probes/sp11-stick-wrapper.h` `sw_sha256`, q1n1 `platform/uefi/sha256.c`); the copy, verify, clean and flush loops are 64-bit (`probes/sp11-stick-load.c`, `probes/sp11-stick-hw.h` `sp11hw_clean_range`). The wrapper's progress counters are `uint64_t` (`bytes_copied`, `bytes_hashed`). The limit is the only change: 2 GiB fits 31 bits plus one, which the C harness holds at both sides (section 7).
- The monitor's box is 64-bit: `watchdog_deadline = now + freq * seconds` (`probes/xnuboot/clock_timer.c:25`), `(watchdog_seconds + 60) * hz` (`cpu_boot.c:289`), and the wrapper compares the PARAMS word as a `uint64_t` (`probes/sp11-stick-monitor.c:148`). The guest's virtual WD1 counter is `uint32_t` and counts the guest's own clock, 24 MHz (`probes/guestprofile.py` `virtual_counter_hz`), so it wraps after 178.96 s (3,435,973,837 ticks of the monitor's 19.2 MHz clock); the wrap stops nothing: the threshold check runs only when the guest set the enable bit and is made before the counter is reduced to 32 bits (`compat/watchdog.c:12-17`), and a reset that the model asks for is a `MON STOP DEVICE_RESET` (`probes/xnuboot/clock_timer.c` `device_reset_stop`). Whether `wdt=-1` leaves that bit clear on the unit is UNKNOWN (INFERRED from the comment at `compat/watchdog.c:34`; boot 28 did not test it: its run ended at 40.08 s, before the wrap at 178.96 s).
- The root is mapped, not read: `probes/ramdisk.py:115-138` `load_ramdisk` returns a read-only `mmap`, `probes/xnuboot.py:2717,2750` puts it in `built['chunks']`, and `load_root_hash` hashes it whole (`ramdisk.py:110`). In `iokit` mode the loader adds `boot-ramdmg-size`, `boot-ramdmg-extents`, `boot-uuid`, `apfs-preboot-uuid`, the root-hash payload, `protected-data-access` 0 and `sepfw-load-at-boot` 0 to `/chosen` (`xnuboot.py:2756-2771`): guest data made by the existing code, which `root-guest` only calls (`tools/sp11_stick_bundle_chunks.py` `real_built`).
- The root has 143 zero stretches of 64 KiB or more, 64.0 MB in all, in 1,862,270,976 bytes (host census, streamed); the table of 1024 entries holds them (46 + 2 x 143 = 332).

## 3. The container and the streaming

`tools/sp11_stick_bundle_source.py` holds the windows: a `Source` is a read-only run of bytes of known length (`BufferSource` over an mmap, `Slice`, `Pieces`, `Generated`). A run of the flattened guest of 256 MiB or more (`STREAM_RUN_MIN`) stays a `Source` (`chunks.flatten`), is padded without a copy, and is cut by `split_run`: the zero stretches of `ZERO_MIN` bytes or more, found page by page and not by a regular expression (the regex is quadratic on the thousands of shorter stretches a root has), become ZERO chunks, the longest first, as many as the table leaves room for (`ROOT_TABLE_FULL` when none fits), and the data between is cut into pieces of at most 128 MiB, so that the wrapper's per-chunk progress word moves every 128 MiB of the copy. Every run shorter than that is cut by the code that always cut it (the tests compare both on the same bytes). `tools/sp11_stick_bundle_root.py` `write_guest` writes the file chunk by chunk, window by window, in the layout of `sb.pack_guest` (compared byte for byte), stepping over every all-zero 64 KiB block so that the file is sparse where the guest is zero; the head and the table are written last. `verify_guest` reads the file back through a `pread` view (not a mapping) and runs the interface's own checks and every digest. `sb.pack_guest` refuses a chunk that is a window of a `Source` rather than read it as a ZERO chunk.

## 4. The `root-guest` command

`SP11_ROOT_BUILD=1 python3 tools/sp11_stick_bundle_build.py root-guest synthetic|real ...` writes `GUEST.DAT` and `root-guest-report.json` below `build/` and nothing else: no PIN.DAT, no PAYLOAD.MAN, no record, no authorisation, so the result is not a bundle and cannot be staged. `synthetic` generates a root of `--root-mib` (SHAKE-128 blocks with zero stretches) and needs no Apple material; `real` needs `--kernelcache`, `--ramdisk` (the raw APFS root, whose SHA-256 the profile pins), `--root-hash`, `--trust-cache` (the profile's own file in the loader's firmware directory) and `--guest-profile` (a profile of the closed menu; default `j700ap-26A428-m1-quiet`, the guest that reached the root wait). `--guest-mib` is a builder value (default of the other builds 384; 6144 is the proposal, 4096 the INFERRED floor, 8192 what the A16 used). The panel is the console, `--sptm-hvc-calls` 0. The built device tree is read back against the tree before deferral (`tools/sp11_stick_bundle_profile.py` `read_back`, as for rung 7), with the properties the loader adds for the RAM root expected with exactly their values (`root_additions`: `boot-ramdmg-size` and `-extents`, `boot-uuid`, `apfs-preboot-uuid`, the root-hash payload under `secure-boot-hashes`, `protected-data-access` and `sepfw-load-at-boot` 0) and no other difference allowed. The command line gets `cpu_boot_timeout_secs=<over the box>` (default the box plus 60) and `wdt=-1` (`boot_arg`, `ROOT_BOOT_ARG`). The RTC is seeded at build from an explicit `--rtc-epoch-us` (the A16 route seeds it at upload, `probes/run.py`): a guest with an unseeded RTC and no epoch is `ROOT_RTC`, and an epoch for a guest without one is `ROOT_RTC` too; the clock then starts at the build's epoch, not at the boot's, which is a limit of a stick that has no upload. The profile is not changed: the menu's profiles have no ACM software mode and no SEP preload, which the A16 recipe (`j700ap-26A428-bootfb-xars-uniform`) adds; whether the base board mounts the root at all was UNKNOWN before boot 28, where the profile with the `acm_fastsim=1` layer ran the stock kernel to `launchd` from the carried root (OBSERVED, section 10).

## 5. Placement and the pair

The unit's bank is 30,720 MiB at `0x880000000`, ending at 2^36. The runner puts a data file at or below `0xFFFFFFFFF`, so GUEST.DAT sits at the top of RAM (INFERRED from an allocation bound; boot 28 placed it at `0XF8D2A1000`, which ends within 2 KiB of the bound: OBSERVED, section 10), and the guest placement must stay clear of the top 4 GiB, the most that q1n1's preload table allows in all: `place-check --root-carry` and `root-guest` refuse a placement that ends above 2^36 minus 4 GiB (`ROOT_PLACEMENT`). The wrapper's own `PLACE_DECLARED` check at run time is the authority. A guest of 6144 MiB with its reserve and work area ends at `0xA28000000`. The pair built with `--root-carry` from the monitor of rungs 5 to 7 (`053a239f...`) is SNAPMON-M1-ACK.BIN `6af26a84...` and SNAPREP-M1-ACK.BIN `562b9b6e...` (built twice from fresh directories, A = B); it is a different pair from every pair of `m1.ACK_PAIRS`, so every record that exists refuses it (`M1_REPORT_MISMATCH`), and every box over 120 s stays refused for the forms that exist (`OPTIONS_BAD`, `LET_PANIC_REFUSED`). A monitor that changes (W6) is a new pair.

NOT RUN by any of them: the verify of a ZERO chunk longer than 4 GiB (it would read 4 GiB; its loop is `sp11sb_zero`, a 64-bit index over a 64-bit count), the cache maintenance and the stores on the unit.

## 11. Rung 10: rung 9's form with the ISC (K18, kept here because docs/SP11-STICK-MONITOR.md is at its size pin; EXPERIMENTAL, hardware NOT RUN, no approval asked)

Rung 10 gives the RAM disk an ISC and changes nothing else of rung 9's form.

The form is rung 9's (`ch.RUNG9_FORM`, the pair `6af26a84...` and `562b9b6e...`, the runner `af76e0bf...`, the profile `quiet-rtc-acm`, `cpu_boot_timeout_secs=360`, a box of 300 s, `--let-panic`, 6,144 MiB of RAM) with one more option, `--isc-image PATH` (`authorisation-template real`, `real` and `root-guest real`). The image is made on the host by `python3 tools/make-isc-fixture.py --build-three-role build/r14/isc-three-role.apfs --size-mib 1025` (1 GiB and a MiB, the smallest container that the macOS formatter lets hold three volumes: OBSERVED on the host): three EMPTY volumes, `Snapintosh-xART` (role 256: the formatter refuses it, so the role is a byte stamped into the unmounted container with its checksum redone), `Snapintosh-Preboot` (16) and `Snapintosh-Hardware` (320). Whether the guest's APFS accepts empty volumes and the stamped role is UNKNOWN.

The guest. The loader (`probes/xnuboot.py`, `isc_image=`) makes ONE RAM disk, the GPT medium of `probes/bootmedia.py`: a protective MBR, a GPT, the root (type `7C3457EF-...`) at 1 MiB, the ISC (type `69646961-...`) after it on a 1 MiB boundary and the backup GPT: 2,939,158,528 bytes at `0X88ED00000`, ending at `0X93E000000`, which leaves 3,104 MiB of the guest's 6,144 MiB free after the 128 MiB that the loader keeps (rung 9's RAM disk left 4,131 MiB). `/chosen` names the whole medium by one `boot-ramdmg-size` and one `boot-ramdmg-extents`; the root hash is over the root partition alone.
