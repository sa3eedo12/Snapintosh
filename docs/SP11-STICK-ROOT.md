# SP11 root carry: Apple's BaseSystem root as the guest's RAM disk, host side

Status: EXPERIMENTAL, hardware NOT RUN. Host only: nothing here was run on the unit, nothing here authorises a run, and no record, no authorisation and no stick tree exists for it. Labels are those of [SP11-STICK-BUNDLE.md](SP11-STICK-BUNDLE.md): VERIFIED (read in a tree, or shown by a host test that ran), OBSERVED, INFERRED, EXPERIMENTAL, UNIMPLEMENTED, UNKNOWN. The design is `files/baseboot-design-2.md` section A2 (design D-A: keep the five files, carry the root as chunks of GUEST.DAT); the runner half is q1n1's `docs/SP11-PAYLOAD-BIGFILE.md` (`Q1N1_SP11_BIGFILE`, W4).

## 1. What changes, and what does not

## 2. Facts (VERIFIED by reading, unless labelled)

- Every size, offset and destination of the interface is `uint64_t` (`probes/sp11-stick-bundle.h`: the chunk and head structures; no `size_t` is used); the hash is q1n1's `q1n1_sha256(const void *, size_t, ...)` with a 64-bit byte count (`probes/sp11-stick-wrapper.h` `sw_sha256`, q1n1 `platform/uefi/sha256.c`); the copy, verify, clean and flush loops are 64-bit (`probes/sp11-stick-load.c`, `probes/sp11-stick-hw.h` `sp11hw_clean_range`). The wrapper's progress counters are `uint64_t` (`bytes_copied`, `bytes_hashed`). The limit is the only change: 2 GiB fits 31 bits plus one, which the C harness holds at both sides (section 7).
- The monitor's box is 64-bit: `watchdog_deadline = now + freq * seconds` (`probes/xnuboot/clock_timer.c:25`), `(watchdog_seconds + 60) * hz` (`cpu_boot.c:289`), and the wrapper compares the PARAMS word as a `uint64_t` (`probes/sp11-stick-monitor.c:148`). The guest's virtual WD1 counter is `uint32_t` and wraps at 223.7 s at 19.2 MHz (`compat/watchdog.c:18`); its threshold check runs only when the guest set the enable bit (`:15`, `:21`). Whether `wdt=-1` leaves that bit clear on the unit is UNKNOWN (INFERRED from the comment at `compat/watchdog.c:34`).
- The root is mapped, not read: `probes/ramdisk.py:115-138` `load_ramdisk` returns a read-only `mmap`, `probes/xnuboot.py:2717,2750` puts it in `built['chunks']`, and `load_root_hash` hashes it whole (`ramdisk.py:110`). In `iokit` mode the loader adds `boot-ramdmg-size`, `boot-ramdmg-extents`, `boot-uuid`, `apfs-preboot-uuid`, the root-hash payload, `protected-data-access` 0 and `sepfw-load-at-boot` 0 to `/chosen` (`xnuboot.py:2756-2771`): guest data made by the existing code, which `root-guest` only calls (`tools/sp11_stick_bundle_chunks.py` `real_built`).
- The root has 143 zero stretches of 64 KiB or more, 64.0 MB in all, in 1,862,270,976 bytes (host census, streamed); the table of 1024 entries holds them (46 + 2 x 143 = 332).

## 3. The container and the streaming

`tools/sp11_stick_bundle_source.py` holds the windows: a `Source` is a read-only run of bytes of known length (`BufferSource` over an mmap, `Slice`, `Pieces`, `Generated`). A run of the flattened guest of 256 MiB or more (`STREAM_RUN_MIN`) stays a `Source` (`chunks.flatten`), is padded without a copy, and is cut by `split_run`: the zero stretches of `ZERO_MIN` bytes or more, found page by page and not by a regular expression (the regex is quadratic on the thousands of shorter stretches a root has), become ZERO chunks, the longest first, as many as the table leaves room for (`ROOT_TABLE_FULL` when none fits), and the data between is cut into pieces of at most 128 MiB, so that the wrapper's per-chunk progress word moves every 128 MiB of the copy. Every run shorter than that is cut by the code that always cut it (the tests compare both on the same bytes). `tools/sp11_stick_bundle_root.py` `write_guest` writes the file chunk by chunk, window by window, in the layout of `sb.pack_guest` (compared byte for byte), stepping over every all-zero 64 KiB block so that the file is sparse where the guest is zero; the head and the table are written last. `verify_guest` reads the file back through a `pread` view (not a mapping) and runs the interface's own checks and every digest. `sb.pack_guest` refuses a chunk that is a window of a `Source` rather than read it as a ZERO chunk.

## 4. The `root-guest` command

`SP11_ROOT_BUILD=1 python3 tools/sp11_stick_bundle_build.py root-guest synthetic|real ...` writes `GUEST.DAT` and `root-guest-report.json` below `build/` and nothing else: no PIN.DAT, no PAYLOAD.MAN, no record, no authorisation, so the result is not a bundle and cannot be staged. `synthetic` generates a root of `--root-mib` (SHAKE-128 blocks with zero stretches) and needs no Apple material; `real` needs `--kernelcache`, `--ramdisk` (the raw APFS root, whose SHA-256 the profile pins), `--root-hash`, `--trust-cache` (the profile's own file in the loader's firmware directory) and `--guest-profile` (a profile of the closed menu; default `j700ap-26A428-m1-quiet`, the guest that reached the root wait). `--guest-mib` is a builder value (default of the other builds 384; 6144 is the proposal, 4096 the INFERRED floor, 8192 what the A16 used). The panel is the console, `--sptm-hvc-calls` 0. The built device tree is read back against the tree before deferral (`tools/sp11_stick_bundle_profile.py` `read_back`, as for rung 7), with the properties the loader adds for the RAM root expected with exactly their values (`root_additions`: `boot-ramdmg-size` and `-extents`, `boot-uuid`, `apfs-preboot-uuid`, the root-hash payload under `secure-boot-hashes`, `protected-data-access` and `sepfw-load-at-boot` 0) and no other difference allowed. The command line gets `cpu_boot_timeout_secs=<over the box>` (default the box plus 60) and `wdt=-1` (`boot_arg`, `ROOT_BOOT_ARG`). The RTC is seeded at build from an explicit `--rtc-epoch-us` (the A16 route seeds it at upload, `probes/run.py`): a guest with an unseeded RTC and no epoch is `ROOT_RTC`, and an epoch for a guest without one is `ROOT_RTC` too; the clock then starts at the build's epoch, not at the boot's, which is a limit of a stick that has no upload. The profile is not changed: the menu's profiles have no ACM software mode and no SEP preload, which the A16 recipe (`j700ap-26A428-bootfb-xars-uniform`) adds; whether the base board mounts the root at all is UNKNOWN.

## 5. Placement and the pair

The unit's bank is 30,720 MiB at `0x880000000`, ending at 2^36. The runner puts a data file at or below `0xFFFFFFFFF`, so GUEST.DAT sits at the top of RAM (INFERRED from an allocation bound; where this firmware puts it is UNKNOWN), and the guest placement must stay clear of the top 4 GiB, the most that q1n1's preload table allows in all: `place-check --root-carry` and `root-guest` refuse a placement that ends above 2^36 minus 4 GiB (`ROOT_PLACEMENT`). The wrapper's own `PLACE_DECLARED` check at run time is the authority. A guest of 6144 MiB with its reserve and work area ends at `0xA28000000`. The pair built with `--root-carry` from the monitor of rungs 5 to 7 (`053a239f...`) is SNAPMON-M1-ACK.BIN `6af26a84...` and SNAPREP-M1-ACK.BIN `562b9b6e...` (built twice from fresh directories, A = B); it is a different pair from every pair of `m1.ACK_PAIRS`, so every record that exists refuses it (`M1_REPORT_MISMATCH`), and every box over 120 s stays refused for the forms that exist (`OPTIONS_BAD`, `LET_PANIC_REFUSED`). A monitor that changes (W6) is a new pair.

## 6. Refusals of the root carry

| Name | Raised when |
| --- | --- |
| `ROOT_GATE_OFF` | `root-guest` without `SP11_ROOT_BUILD=1` |
| `ROOT_INPUT_BAD` | `--ramdisk`, `--root-hash` or `--trust-cache` is not a file, the trust cache is not the loader's own, the profile is no RAM-disk root profile, or the chunks do not hold the whole root |
| `ROOT_BOOT_ARG` | `cpu_boot_timeout_secs` is not over the box, or over 86400 |
| `ROOT_PLACEMENT` | the placement ends above 2^36 minus 4 GiB |
| `ROOT_NO_ROOM` | less than 20 GiB would stay free after the file is written |
| `ROOT_TABLE_FULL` | the chunks of the guest do not fit the 1024 entries, even with no ZERO chunk of the root |
| `ROOT_RTC` | the RTC seed is missing for a guest that has a clock, or refused (no clock, out of range) |

Also the interface's own (`GUEST_COUNT`, `CHUNK_EOF`, ...), `OPTIONS_BAD` (a box outside 1 to 1200 s), `OUT_DIR_REFUSED`, `OUT_NOT_EMPTY`, `Q1N1_TREE_ABSENT` (`--bigfile` with a q1n1 tree whose manifest tool has no `chunk_cap_kib`) and `BUILT_SHAPE`.

## 7. Tests

`python3 tools/test-sp11-stick-bundle-big.py` (Q1N1_SP11_TREE set to the tree with the W4 patch): the sources and the zero-stretch scan against the regex at every boundary; the writer against `pack_guest`; sparse output; the damaged file; the limit at 2 GiB from both sides with and without the context; the lazy run against the joined run on the synthetic guest; the mapped root under the table budget; the command's gate, refusals, determinism and report; the manifest tool with a 300 MiB sparse file; `place-check`; a sparse container of exactly 2 GiB through the C header (`tools/test-sp11-stick-bundle-big.c`: AddressSanitizer, UndefinedBehaviorSanitizer and the implicit-conversion checks; the digest callback reads the data with `pread`, so the maximum resident set is a few MiB) with the gate on and off, a damaged byte, a file one byte longer and one shorter, the seeded faults that narrow the length and that hash through the mapping (a 600 MiB container, so that no run holds more than 1 GiB); and the box ceiling matrix (`-fsyntax-only` of `probes/sp11-stick-monitor.c` with the gate and cap on and off).

## 8. UNKNOWN and not done (never guessed)

UNIMPLEMENTED: the ISC. `root-guest` passes no `isc_image` to the loader, so the guest has the root alone. The ISC tool that was committed since (main repo `e6c1751`, `tools/make-isc-fixture.py --build-three-role`) makes a scratch image of 1.5 GiB with the roles 256/16/320, which is more than the 256 MiB that design note A2 assumed: the medium is about 1 GiB of ISC plus the root plus a tail (INFERRED from that report), and as chunks it fits the 2 GiB of one GUEST.DAT only to the extent that the ISC is zero (ZERO chunks cost no file bytes) and the table holds the entries. A guest with it needs this command extended and measured.

UNKNOWN: a read into a buffer above 4 GiB has never been observed on the unit (the runner's own list); the unit's firmware placement of a 1.8 GiB allocation and whether it is one memory-map descriptor; the stick's read rate at this size; the time of an 8 MiB flush operation; whether `wdt=-1` keeps the guest's WD1 counter unarmed; whether the quiet profile with this root mounts it without ACM software mode and the SEP preload; the guest RAM the root needs (4096 MiB is INFERRED); the guest's wall clock after a boot that started later than the build's RTC epoch. A record for any of it is a separate commission.
