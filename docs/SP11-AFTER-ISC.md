# SP11 after the ISC: what the stock kernel and launchd need once rung 10's ISC is there (host analysis; hardware NOT RUN)

**Status: EXPERIMENTAL. A host analysis of the guest's inputs (the J700 26A428 kernelcache, the BaseSystem image, the device tree and this repository) and of runs of the host's own macOS tools. It is not a hardware result and it authorises nothing. Hardware: boots 1 to 31 only; nothing newer has run. Rung 10 (the root plus the three-role ISC, [SP11-STICK-ROOT.md](SP11-STICK-ROOT.md) section 11) is prepared and not booted: its record (SHA-256 `098da57967372a02f0cf615d4cf0059ca62276d36e397e809cd6d85e3aeb098a`, tools commit `08a208d`) was approved for one boot and its files are staged, and that boot has not run, so rung 10 has no result in this repository.** What follows is a set of predictions that the film of that boot will settle (section 8).

The note extends the host reading of the BaseSystem image that STICK-ROOT sections 8 and 11 cite (an earlier "boot-tasks note", kept outside this repository), answers the two questions that [SP11-KERNEL-STOPS.md](SP11-KERNEL-STOPS.md) section 7C left open (what the boot tasks after `mount-phase-1` need, and whether an ISC with no content satisfies it) and corrects the earlier reading in four places (section 7).

## 2. Verdict

- **The kernel's APFS accepts the ISC, by reading and by a host run; the guest's own kernel is UNKNOWN until rung 10.** VERIFIED (read): the kext's `AppleAPFSDiags` personality matches the iSC-typed slice, the container scheme scans it and three `AppleAPFSVolume` nodes appear with `Role` arrays ("xART", 256), ("Preboot", 16) and ("Hardware", 320). Nothing on the mount or scan path validates a role (INFERRED for a call through a pointer, which the scan cannot see): roles choose a string, a mount-flag set and an expected mount point. VERIFIED (host run): the host's own AppleAPFS, on the actual fixture and on a GPT medium of `probes/bootmedia.py`'s geometry, gives the same answer: `fsck_apfs -n` says OK for the container and the three volumes, and all three mount read-only and read-write. The stamped xART role is therefore not a kernel-side obstacle by reading and by a host mount. Limits (section 3.3): the host kernel is 27.3 and the guest's 26A428, a disk image stands for a RAM disk, and the guest has no SEP.
- **`mount-phase-1` needs one ISC volume.** VERIFIED (read): the only mandatory ISC item is the xART volume (role 0x100) at `/System/Volumes/xarts`; the iSCPreboot (0x10) and Hardware (0x140) steps on the ISC print `Ignoring` when they fail. The three-role image is more than the task needs. If the xART step fails its text is `mount_phase_one:1922: xART volume mount failed - error ...` (the line number is read from the binary) and the task aborts (section 3.4).
- **No SEP or xART service is on the path to the first stops.** VERIFIED (read): the kernel's APFS has no xART or SEP linkage beyond the role string, the entitlements for creation and the mount-point map; `xartstorageremoted` launches only on an ACPI node named `APP7777`, which the J700 tree does not have; the data-protection task reaches "Skipping SEP firmware load" before any xART code (the flow is VERIFIED, read; that it exits 0 is INFERRED); AMFI's local signing is switched off by `protected-data-access` = 0 with a log line (the reading is VERIFIED, read; the outcome INFERRED).
- **Four corrections to the earlier boot-tasks note (INFERRED; section 7).** (1) `prebootensurer`, in this container (no Recovery-role volume in the boot volume group), takes an early branch that prints a line and exits 0, so `restore-datapartition` is not the likeliest first real stop: the likeliest hard stops move to after "Early boot complete" (EL0 stability, the daemons `logd` and `kernelmanagerd` that launchd panics on when they crash consecutively, memory). (2) `data-protection` is not silent: it prints "Skipping SEP firmware load". (3) The Recovery UI is started by `recoveryosd` (`OnDemand` false) with `Installer Progress` (`RunAtLoad`); `loginwindowLite` is for the fvunlock mode only. (4) The role and partition facts that the earlier note labelled INFERRED are now VERIFIED (read: the personalities) and VERIFIED (host run: the host medium test).
- **UNKNOWN until the film of rung 10:** whether the ten `wait_for_node` rounds of boot 28 disappear on the unit; whether the guest's kernel publishes the slice of its RAM-disk medium; the first stop after `mount-phase-1`.

## 3. The ISC and the kernel

### 3.1 From the slice to the volume node (kernel; VERIFIED, read, unless marked)

- AppleAPFS is the fileset entry `com.apple.filesystems.apfs` (VA `0xfffffe0007ca8d40`, file offset `0xca4d40`). Its I/O Kit personalities (the kernelcache's `__PRELINK_INFO` property lists): `AppleAPFSContainerScheme` (provider `IOMedia`, Content Hint `7C3457EF-0000-11AA-AA11-00306543ECAC`, probe score 2000); `AppleAPFSContainerSchemeWholeDisk` (Whole = true, 2000; INFERRED to be the one that took boot 28's raw medium); `AppleAPFSDiags` (Content Hint `69646961-6700-11AA-AA11-00306543ECAC`, the iSC slice type, class `AppleAPFSContainerScheme`, 2000); `AppleAPFSRecovery` (`52637672-7900-...`); `AppleAPFSContainer` (Content Hint `EF57347C-...`, the `AppleAPFSMedia` a scheme publishes); `AppleAPFSMediaBSDClient` and `AppleAPFSVolumeBSDClient`.
- Slice type `69646961` therefore reaches `AppleAPFSContainerScheme` (its start function is at `0xfffffe000b528a10`, which also reads the `apfs_swcrypto_sbufcount` and `lbufcount` boot-args; its error texts are "failed to alloc SW crypto", "failed to init filter" and "failed to start"), then `AppleAPFSMedia`, `AppleAPFSContainer` and one `AppleAPFSVolume` per volume. Reproduced on the host (VERIFIED, host run: section 3.3).
- The root choice is unambiguous with two containers. `IOHDIXController`'s `findAppropriateIOMediaObject` (strings next to `di-root-ram-file`) considers slices of type `48465300` and `7C3457EF`, `Apple_HFS(X)`, or a whole medium that is a leaf or has an `AppleAPFSContainerScheme` child; the iSC type is never a root candidate. `container_rootmount` (function at `0xfffffe000b523208`, "boot from ramdisk") then asks `valid_bootable_volume` (`0xfffffe000b524028`) for the first volume whose role is 1 (System), else the first non-empty file-system oid. The strings and cross-references are VERIFIED (read); the selection logic is INFERRED.
- A function whose `__func__` is "init" (`0xfffffe000b5064b0`; INFERRED to be `AppleAPFSVolume::init`) sets Content Hint `41504653-...` and calls the property publisher (`0xfffffe000b506700`). It publishes `FullName`, `RoleValue` (the u16 at +0x3c4 of the in-memory volume superblock, which is the on-disk `apfs_role` at +964, the field the stamp writes), `Role` (an array of one string chosen by a switch over the role: 18 names, from Update to Internal), `IncompatibleFeatures`, `VolGroupUUID` and `Encrypted`. It compares and rejects nothing (INFERRED from the function's call list and the order of its literals).

### 3.2 Where the role is checked, and where it is not

- **Creation policy (VERIFIED, read).** `apfs_is_volume_role_allowed` (`0xfffffe000b5cb16c`) has two direct callers, `apfs_newfs` (`0xfffffe000b512430`) and `apfs_getset_role` (`0xfffffe000b5206d4`); a call through a pointer would not show in the scan (INFERRED). The texts around it ("not allowed on this container", "not allowed for an unencrypted volume", "Encrypted volume is not allowed ...", the entitlement `com.apple.private.apfs.xart` with "Creating an xART volume without entitlements ...", the entitlement `com.apple.private.apfs.change-special-role` with "cannot change role of xART volume") describe creation. The host formatter refuses to make the xART role (VERIFIED, host run: `newfs_apfs` says "not allowed to create volume with role 256" and `diskutil apfs addVolume -role X` fails with -69624) although the host `newfs_apfs` itself carries `com.apple.private.apfs.xart`; the cause of the refusal is not established (the runs were unprivileged). The ISC image carries the role as a byte stamp ([SP11-STICK-ROOT.md](SP11-STICK-ROOT.md) section 11). The creation policy is not on the mount path.
- **Role compares (VERIFIED, read).** Every u16 load at +0x3c4 in the kext was listed (137 sites in 88 functions) and the compare immediates within 23 instructions of each load were collected (a jump-table switch is invisible to that scan: INFERRED). Compares to 0x100 or 0x140 occur in `apfs_is_volume_role_allowed`, the property publisher, `handle_mount`, `apfs_is_on_designated_isc_mount` (`0xfffffe000b5995d4`) and a snapshot-entitlement helper (`0xfffffe000b5013e4`); compares to 0x10 also occur in the TDM check (`0xfffffe000b5246f4`) and in an unnamed function at `0xfffffe000b543c58`. A rescan by the independent fact-check found 134 loads in 88 functions and two compare sites that this list lacks (`0xfffffe000b4f72a8` and `0xfffffe000b56cbcc`), neither on the mount path as far as it traced (INFERRED).
- **The mount path (names VERIFIED, read; behaviour INFERRED; the flag sets VERIFIED, host run).** `apfs_vfsop_mount` (`0xfffffe000b576e94`) calls an eligibility check (`0xfffffe000b5246f4`: it special-cases only role 0x10, otherwise it walks the registry ancestors and asks for a property named `AppleTDMLocked`; the System volume passed it in boot 28, OBSERVED, and xART takes the same branch, INFERRED) and then `handle_mount` (`0xfffffe000b56f430`). Role effects there are flag sets: roles 4, 0x10, 0x20, 0x1c0, 0x240, 0x280, 0x2c0 and 0x300 get `MNT_DONTBROWSE`; roles 8 and 0x100 get `NOEXEC | DONTBROWSE | NOATIME` (`0x10100004`; for role 8 the mount path is first compared with `/System/Volumes/VM`); roles 1 and 0x40 have volume-group handling; only role 0x40 has a panic ("unencrypted data volume is not allowed", function `0xfffffe000b579f10`).
- **ISC recognition (VERIFIED, read; the outcome INFERRED).** The function at `0xfffffe000b508ebc` walks the registry ancestors for a Content Hint and `handle_mount` compares it with `69646961-...`. On a match `apfs_is_on_designated_isc_mount` maps role 0x10 to `/System/Volumes/iSCPreboot`, 0x100 to `/System/Volumes/xarts` and 0x140 to `/System/Volumes/Hardware`; any other role logs "unexpected volume role ..., not on iSC" and returns 0. A match logs "volume with role ... will be mounted until ..." and sets a system-mount flag. No error is returned from this check (INFERRED). Whether that apfs log line reaches the console is UNKNOWN.

### 3.3 The stamped xART role

- **The fixture (VERIFIED, read; a parse of the ISC image, 1,074,790,400 B).** The container superblock has features 0, incompatible features 0x2, `max_file_systems` 3, file-system oids 1026, 1030 and 1032 and checkpoint xids 1 to 4. There are three volume superblocks with features 0x2, read-only-compatible features 0, incompatible features 0x1 (case-insensitive), `fs_flags` 0x1 (unencrypted), all counters 0, and roles 0x100, 0x10 and 0x140 at +964. Every checkpoint block and volume superblock re-checksums correctly (Fletcher-64). The three volume superblocks carry the same formatter string (`newfs_apfs 3288.60.11.0.1`), feature words and counters and differ in identity fields (oid, UUID, name) and the role u16.
- **A clone of the fixture (VERIFIED, host run; `cp -c`, attached `-nomount -readonly`).** The registry shows `Role` ("xART") with `RoleValue` 256, ("Preboot") 16 and ("Hardware") 320. `fsck_apfs -n` prints "appears to be OK" four times (three volumes and the container) and no error word. `mount -t apfs -o rdonly,nobrowse,noexec` succeeded for all three, and so did read-write mounts of a writable clone. The kernel itself added `noatime` for the xART volume only (the options passed were `rdonly,nobrowse,noexec`), which is exactly the flag set read in `handle_mount`. The host's own real ISC (`ioreg`) has an xART volume with `RoleValue` 256, unencrypted, `IncompatibleFeatures` 1: the same shape as the fixture.
- **A GPT medium of `probes/bootmedia.py`'s geometry (VERIFIED, host run).** Sizes from `layout()`, a stand-in zero root slice, the fixture as the iSC slice, 2,151,677,952 B sparse; `bootmedia.inspect` passes. The host's `IOGUIDPartitionScheme` lists `Apple_APFS` and `Apple_APFS_ISC`, and the iSC slice publishes its own container with three volumes and the roles above. This tests the GPT, the type GUIDs, the 512-byte sectors and the `AppleAPFSDiags` match; it does not test the guest's RAM-disk path.
- **Limits (UNKNOWN).** Host kernel 27.3 against the guest's 26A428 (27.0); the guest's medium is the `boot-ramdmg` RAM disk and the host's a disk image; the guest has no SEP. Documentary precedent only, not re-run here: the A16 chain's BaseSystem route, which carries a separate iBootSystemContainer image holding the xART, Preboot and Hardware volumes that `apfs_boot_util` waits for, reached up to 70 processes ([GUI-BOOT-ROADMAP.md](GUI-BOOT-ROADMAP.md) sections 4 and 5), and [FULL-INSTALL.md](FULL-INSTALL.md) seeds its ISC from a 256 MiB xART image.
- **Version risk (INFERRED).** The formatter is 27.3 and the guest's kernel is 27.0; that matters only through feature bits. The fixture's are the long-standing set (incompatible 0x2 and 0x1, unencrypted) that the 27.3 host's own xART volume also has.

### 3.4 What mount-phase-1 does with it (userspace; VERIFIED, read, unless marked)

- The binary that prints boot 28's lines is `/System/Library/Filesystems/apfs.fs/Contents/Resources/apfs_boot_util` (112,288 B): its function names are the prefixes in boot 28's text (`mount_by_role:451`, `mount_by_role_if_present:556`, `mount_phase_one:1914`, `wait_for_node:266` and `:272`). launchd runs it as the task `mount-phase-1` (`/sbin/mount -P 1`). `volcnt = 0` is a constant in the print call (VERIFIED, read), printed when the lookup returns no array; status 49245 is 0xC05D, the tool's own not-found code (errno 93 in the Update line, OBSERVED).
- Its calls: APFS.framework `APFSVolumeRoleFind`, `APFSVolumeRole`, `APFSVolumeCreate` and `APFSGetVolumeGroupID`; I/O Kit `IOServiceAddMatchingNotification` (class `AppleAPFSVolume` for a role with an index: xART 5, Preboot 3, Hardware 4; `AppleAPFSContainer` only for index 0), `IORegistryEntryGetParentEntry` and `IORegistryEntryCreateCFProperty` for "Content Hint" and "Role" (the `Role` array must hold exactly one string) and `IOServiceWaitQuiet`; `mount(2)` and `fsctl`. The ISC container is found only by the Content Hint of the `IOMedia` above the `AppleAPFSMedia` (`69646961-...`), after one scan of the nodes that already exist, in run-loop rounds of 3.0 s, ten rounds, and never by UUID or volume group: it waits for an `AppleAPFSVolume` whose one-string `Role` is that role's name and whose ancestor `IOMedia` carries the hint; others are passed over without a line.
- The order of `mount_phase_one` (roles passed to `mount_by_role`, from the code): VM (8; silent in boot 28), Preboot (0x10) read-only on the root container, if present; Update (0xC0), `Ignoring`; **xART (0x100) on the ISC at `/System/Volumes/xarts`: FATAL**, `mount_phase_one:1922: xART volume mount failed - error ... (errno ...)` and the task aborts (`abort_with_reason`, reason "xART volume mount"): launchd reports "exited due to SIGABRT" as in boot 28 (OBSERVED), not an exit status; FactoryLogs (0x20), `Ignoring` (line 1927); Diags (0x280), internal builds only; iSCPreboot (0x10) on the ISC, `Ignoring` (1939); Hardware (0x140) on the ISC, `Ignoring` (1944); exit 0. A lookup that finds the node but cannot mount prints "unable to mount ... failing bootstrap" first. Expected pass lines (INFERRED from format strings): "Mounting ... on /System/Volumes/xarts", then the FactoryLogs failure pair (`mount_by_role:451` "failed to find volume with role = 20 ..." and `mount_phase_one:1927` "Log volume mount failed - error c05d (errno 93). Ignoring..."), then "Mounting ..." for iSCPreboot and Hardware. The print gate is a level word at `0x100010004` that holds 5; no store to it was found (VERIFIED, read; a store through a pointer would not show: INFERRED). The "Mounting" lines need a level of at least 5, which is met exactly, and the other lines are at level 4 or below. A line that is not a failure: "Non-desired APFS node found...", a new volume node that arrived during a wait round and was not the wanted one; it prints only inside a wait round.
- No volume content is read by the task: no UUID, name, file, record or manifest check (VERIFIED, read). Empty volumes suffice at this step (INFERRED). The task requests the xART, iSCPreboot and Hardware mounts read-write (read-only argument 0 at `0x1000021bc`, `0x10000229c` and `0x1000022f0`; VERIFIED, read; the three volumes of a writable clone mount read-write on the host too, section 3.3); a read-write mount writes into the guest's RAM copy of the ISC (checkpoint blocks), which is harmless to the stick (INFERRED: it is a copy in guest memory).

### 3.5 SEP and xART services, and their absence

- **Kernel (VERIFIED, read).** The kext's xART strings are the role name, the two entitlements, the mount point and the role messages above; there is no `AppleSEP*` call. `AppleSEPManager`'s `AppleSEPXART` (gigalocker, epochs, "Fetched/Saving %s-xART") needs a running SEP and is entered from userspace (`seputil` gigalocker-init, `xartstorageremoted`); neither runs here (INFERRED). The J700 device tree has `/arm-io/sep/iop-sep-nub` with child nodes `xART`, `Sandcat` and `InvalidateHmac` (xART has only a name; AMFI and AppleLockdownMode test its path, not a property) and no ACPI node `APP7777` (0 hits).
- **AMFI (VERIFIED, read).** The local-signing gate (function `0xfffffe0009717824`) tests `allow3rdParty`, the `-restore` boot-arg, the xART node plus the `/chosen` property `protected-data-access`, `oblit-inprogress`, then asks AKS. The loader writes `protected-data-access` = 0 for the RAM-disk profiles (`probes/ramdisk.py` `populate_ramdisk_policy`, lines 73 to 93), so the outcome is the log line "AMFI: disabling local signing ..." (INFERRED). The assertion "calling %s without xART storage support" fires only where the xART node is absent, which is not the case here.
- **Credential manager.** `AppleCredentialManager` logs "Timer state [NOT read/written] ... due to noXART" (string VERIFIED, read; that it tolerates the absence is INFERRED). `acm_fastsim=1` and `sepfw-load-at-boot` = 0 already carried boot 28 to launchd (OBSERVED).
- **Userspace (VERIFIED, read).** `xartstorageremoted` never launches (its event is an `IOACPIPlatformDevice` named `APP7777`: plist and device tree); `applekeystored` is triggered by a Mach service and `keystore-init` is skipped in the BaseSystem. In the BaseSystem image 16 binaries name `/System/Volumes/iSCPreboot`, `Hardware` or `xarts`, among them `kernelmanagerd` and `kernelmanager_helper` (both `_PanicOnCrash`), `IOMFB_bics_daemon`, `airportd`, `mobileactivationd`, `sysstatuscheck` and `kmutil`. What they do with the empty volumes is UNKNOWN: a panic naming `kernelmanagerd` after "Early boot complete" may come from that, not only from EL0 faults. `seputil` uses `/System/Volumes/xarts` only to build a `<path>/<id>.gl` gigalocker file name (function `0x10000884c`, called from the command handlers at `0x100004820`, `0x100005434`, `0x10000689c` and `0x10000694c`), none of them on the skip path of section 4; with a live SEP and a non-zero `sepfw-load-at-boot` the xART volume's content would start to matter, which is outside rung 10 (INFERRED).
- **AppleSEPKeyStore and AKS.** APFS reaches AKS only on the encrypted-volume branch of the property publisher (`apfs_vek_get_aks_state`, "AKSFileVaultServices"); the fixture's volumes are unencrypted (INFERRED). AMFI asks AKS only after the gates above. The kernelcache carries `AppleSEPKeyStore`, `AppleSEPManager`, `AppleCredentialManager` and `AppleFDEKeyStore` as fileset entries (VERIFIED, read); without a SEP they cannot complete a SEP session, and boot 28 reached launchd without it (OBSERVED).
- **Rootless.** If anything entitlement-gated touched the ISC devices, the kernel's SIP table (`com.apple.rootless.volume.iSCPreboot`, `iSCHardware`, `iSCRecovery`; xART has none) is keyed by role and by the same Content Hint, and `apfs_boot_util` is Apple-signed (INFERRED).

### 3.6 What would falsify the reading, and what it would look like (INFERRED)

- **The ten `wait_for_node` rounds again, with launchd running:** the media path or the volume's `Role`: an unpublished slice, a container that did not start, a wrong ancestor Content Hint and a mismatched `Role` string all give the same silent rounds (a malformed `Role` also prints the "roles ..." lines below).
- **`xART volume mount failed - error ...` after "Mounting ..." lines, or the "unable to mount ... failing bootstrap" line:** the kernel refused the mount; the errno and the apfs line before it are the result. By the reading, the kernel refuses a role nowhere on this path.
- **A kernel panic naming apfs** ("unencrypted data volume is not allowed" is the one role-keyed panic found, role 0x40 only) **or `iokit_rootless.cpp`** ("SIP recorded the same protected device ...": two devices recorded with different entitlements; not expected with distinct volumes).
- **"AppleAPFSContainerScheme failed to start" or "failed to alloc SW crypto" kernel lines:** the scheme could not start for the slice (role-independent).
- **"roles has more than one entry" or "not a string" from `apfs_boot_util`:** the `Role` property is not the single string read above.

### 4.1 restore-datapartition and prebootensurer (the earlier stop, re-read)

The script's commands in order (VERIFIED, read): `bs-data-tasks -P 1`; `umount -f -v -A -t tmpfs`; `mount_tmpfs -s 2560 MiB /System/Volumes/Data` (a cap, not an allocation; the boot-arg `bs_data_size=N` (MB) changes it); `ditto` of the 3.3 MB template (it creates `/etc`, `/var` and `/Library`); `mkdir`s; `setlanguage`; `mount_tmpfs -s 32 MiB /Volumes`; `prebootensurer`; `bs-data-tasks -P 2`.

- **`bs-data-tasks`** (54,896 B; "only as an early boot task", "not outside the BaseSystem"). Phase 1 asks `fsctl` GET_DEV_BY_ROLE for the Data volume; with none it prints "stash_data_volume_unlock_record: fsctl(APFSIOC_GET_DEV_BY_ROLE) error: N" and returns 0 (INFERRED from the code). Phase 2 syncs the time zone with Preboot ("No accessible timezone content ...") and handles migration-mode mounting: warnings (INFERRED).
- **`prebootensurer`** (74,608 B; `main` at `0x100002190`). After its early-boot and BaseSystem checks it reads `/chosen` `boot-uuid`. The path is chosen by the boot-arg `-post-upgrade` (absent here); the first lookup is the `AppleAPFSVolume` whose UUID is the boot-uuid and whose `RoleValue` is 4 (Recovery); the kcgen test comes after it and is not reached. The earlier note's "`boot-objects-path`, which nothing writes" is therefore not a blocker.
