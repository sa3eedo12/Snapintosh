# SP11 M1 guest profiles: the menu of device trees

Status: EXPERIMENTAL host-side tooling; hardware: the profile `quiet` was booted once (boot 27, rung 7; OBSERVED, one unit, one boot; section 6), and NOT RUN for every other profile of this menu and for any other boot of `quiet`. Labels: VERIFIED = a source read or a host run that is named; OBSERVED = boots 20 to 27, as the operator's films show them; INFERRED; UNKNOWN. No Apple byte is quoted: names, hashes and counts only.

## 1. What a profile is

`--guest-profile NAME` (`real` and `authorisation-template real` of `tools/sp11_stick_bundle_build.py`) names the device tree that the guest kernel is given. A profile is a virtual board description: the base board `j700ap-26A428` (the default, and the board of every bundle so far) plus a fixed union of whole ROOT SETS. A root set withdraws device-tree roots that the M1 monitor has no model for, so that the kernel never attaches to them; the A16 route did the same, root by root, and never used a catch-all (`probes/deferred.py`). Nothing is claimed about the unit beyond that: the A16 reasons for each root are comments of the A16 chain (INFERRED for the SP11), and a withdrawn device is unavailable, never reported as started.

A profile changes the DEVICE_TREE chunk and the one word of the HANDOFF page that holds the tree's length (`boot_args.deviceTreeLength`), and nothing else: PARAMS and the 120 device models are the base board's, and the frozen monitor pair (SNAPMON-M1.BIN, SNAPREP-M1.BIN) is not touched (VERIFIED: `tools/test-sp11-m1-guest-profile.py` `Guest`, with the kernelcache; two of the 46 chunks differ). One profile, `quiet-rtc`, is the exception: it has the quiet device tree and binds the PMU's real-time clock, which changes three words of one device model in PARAMS and nothing else (section 7). A build without the option, or with the default's name, is byte for byte what it was. It is not a pass criterion of any record.

The sets are not independent, and the needs are measured, not assumed: with the set left out, the loader's own guard refuses the base tree (a retained node still points at a withdrawn provider): `dcp` without `dcpext` (dispext0 function-send_disp_clock names disp0); `smcbtm` without `aop` (the Stockholm node of aop-spmi0 names smc-pmu), without `dcp` (disp0 function-pmu_ram_access) and without `audio` (audio-hp-mic function-input_power_enable).

`smcbtm` is one unit and no profile can split it. Without btm and the four btm functions of ppm, pmu-main returns once its SMC function is withdrawn and btm is published, which panicked the A16 (AppleCotaBTM::configSampling, "unable to config PMU", generations 64 and 65: a comment of the A16 chain, INFERRED here). The loader's guard cannot see that trap: it accepts smc without btm (VERIFIED), so the menu refuses it (`GUEST_PROFILE_SPLIT`). `smc-gpio` is not in the set: the A16 retains it and the base board models it.

Not offered: the four jpeg roots (jpeg0-h17a, jpeg0-h17p, jpeg1-h17a, jpeg1-h17p). The A16 chain has no pin for them; a pin is the digest of a generated subtree and a new one is a decision of its own. The host analysis of boot 26's stop (`files/stopsite-r8.md`, a file and not a run) INFERS that the JPEG engine's driver is the first of them that the kernel probes once the accelerators are withdrawn, so that rung 7's record names an S2_FAULT in its window as a possible next stop.

## 4. The option, the refusals and the read-back

The list is closed: the ten names of section 3 and nothing else; a profile that `probes/guestprofile.py` registers for the A16 route is not admitted. That file is unchanged and does not import the menu: the builder registers the nine profiles when it starts (`register()` of `probes/guestprofile_m1.py`), so the A16 route's tools, which copy and hash `guestprofile.py` alone, never see them. Every refusal prints `REFUSED=<NAME>` before any guest is built, except the read-back:

- `GUEST_PROFILE_REFUSED`: a name outside the list; a profile in any form but rung 7's and rung 8's (sections 5 and 7); a profile of the list other than `quiet` in rung 7's form or `quiet-rtc` in rung 8's (their predictions and falsifiers are written for the roots that `quiet` withdraws and for the clock: nothing is predicted for any other set, UNKNOWN); and the other way round, rung 7's box and word (120 s, `cpu_boot_timeout_secs=120`) without a profile, which is a form of its own that the closed list of the acknowledging monitor does not hold (`ch.ACK_FORMS`).
- `BOOT_ARG_REFUSED`: a word outside the closed list (`cpus=1`, `cpu_boot_timeout_secs=120` and `cpu_boot_timeout_secs=90`), `nested_panic_max` among them: no form of any record carries it (unproven, and rung 7 does not need it).
- `GUEST_PROFILE_SPLIT`: a registered profile that is not the base board and whole root sets (a set only partly withdrawn, a set without the sets it needs, another field).
- `GUEST_PROFILE_READBACK`: after the loader has built the guest, the builder rebuilds the tree before any deferral from the same state and checks the published DEVICE_TREE chunk against it: every pin is the digest of its subtree before deferral; exactly the nodes under the profile's roots are missing; every other node, property and child list is the generated one but for the declarations withdrawn; the chunk is the serialisation of the tree it parses to; the device models are the loader's own (with the clock model seeded at the menu's constant for `quiet-rtc` and with none for any other profile) and the PARAMS chunk is their serialisation. The default board is not read back.
- `PANEL_MISMATCH`: the finished guest is not rung 6's but for the device tree and the HANDOFF page's two fields (section 5).
- `PIN_STRING`: a facts label that starts with a mark, or does not fit (section 5).

An approved record binds the label and the guest's digest, so the bundle of rung 7 under the approved record of any other kind (the five older ones, rung 5's and rung 6's) and each of those builds under rung 7's record end `REFUSED=AUTH_RECORD_MISMATCH`, and nothing is written (host run: `tools/test-sp11-stick-monitor-rung7.py` `Builder`, with the stand-in loader; the regeneration script of the session repeats it with the real guest).

## 5. Rung 7: the one record that carries a profile (EXPERIMENTAL)

Two forms carry a profile, `quiet` in rung 7's and `quiet-rtc` in rung 8's (section 7): rung 6's form (`--m1-run --panel console --cpu-start ack --let-panic --time-box-s 120 --sptm-hvc-calls 0`, the acknowledging pair `SNAPMON-M1-ACK.BIN` and `SNAPREP-M1-ACK.BIN`, rung 6's own) with `--boot-arg cpu_boot_timeout_secs=120 --guest-profile j700ap-26A428-m1-quiet`. The acknowledging monitor's closed list is exactly four forms (`ch.ACK_FORMS`): rung 5's (60 s, word 120), rung 6's (120 s, word 90), rung 7's (120 s, word 120, with the quiet profile and with it only) and rung 8's (the same box and word with `quiet-rtc` and with it only). Every other form with a profile is `GUEST_PROFILE_REFUSED`, before any guest is built: a record of a profile guest says what its profile and its words change (`tools/sp11_stick_bundle_panel_rung7.py`, `..._rung7d.py`, `..._rung8.py`, `..._rung8d.py`, `tools/sp11_stick_bundle_panel_profile.py`), and the older kinds' words, which say that their guest differs from the base guest in one word, would be false of it. The other seven profiles stay in the menu until a record text exists for them.

**The command line.** The word is rung 5's, `cpu_boot_timeout_secs=120`, so that XNU's wait for the CPU that never starts would end about 122 s after the guest's first CPU-start store, outside the box of 120 s by a margin of about 2 s (INFERRED, host analysis `files/stopsite-r8.md` of the session: a file and not a run) and cannot cut the run at 92 s as rung 6's 90 would have. `nested_panic_max` is in no form: the nested-panic cycle of boot 24 is a stop that this guest is not asked to reach, and the setting is unproven.

**The label.** PIN.DAT holds 23 characters of label (`PIN_LABEL_MAX`). The label is `M1RUN-`, the marker of the guest's choices (none, `PANEL-`, `CONSOLE-`, `CPUS1-`, `LETPANIC-` for `--let-panic` with the plain monitor, `ACKPANIC-` for the acknowledging monitor), the mark of the profile (none for the base board; two characters from section 3), and the facts label: rung 7 is `M1RUN-ACKPANIC-Q-RUNG7` (22 characters; a facts label of up to six characters fits), distinct from rung 6's `M1RUN-ACKPANIC-RUNG6` and rung 5's `M1RUN-ACKPANIC-RUNG5` by the mark, which a facts label may not start with, nor with a marker. The other kinds keep the facts' label. The facts file of the real path is rung 6's with the label `RUNG7` (`build/m1p/sp11-facts-rung7.local.json`, git-ignored); the accounts of boots 25 and 26 in the record are keyed blocks in the text module, not facts.

**What the guest is against rung 6's own.** `compare` (`tools/sp11_stick_bundle_rung7.py`) holds the finished chunk table to the table of rung 6's own bundle that the module pins (46 chunks, `RUNG6_CHUNKS`: the bundle of boot 26, record `d9d79c87...5cda`, regenerated by the session's script): exactly chunks 0 (HANDOFF) and 3 (DEVICE_TREE) differ, PARAMS (chunk 2) and the other 43 are rung 6's byte for byte, and chunk 0 with its two fields put back (the length of the tree, `deviceTreeLength` at +0x68 of boot_args, and the command line at +0x6C) has rung 6's SHA-256: `PANEL_MISMATCH` otherwise. Every "differs from rung 6" sentence of the record is made from what it returns. Host run on the kernelcache: 395 nodes become 352, the DEVICE_TREE chunk 350,576 to 327,664 bytes, GUEST.DAT 118,908,480 to 118,885,568 bytes, and the command line ends `cpu_boot_timeout_secs=120` in place of `=90`.

**The windows of the withdrawn nodes.** The record of rung 7 tells the coordinator that a MON STOP S2_FAULT with A= in a window of a withdrawn node means that the profile did not take. Those windows are the reg of the 43 nodes through the ranges of arm-io, less the windows that a retained node covers (`tools/sp11_stick_bundle_windows.py`): the video decoder's 0X380000000..0X381404000 but not its DART's 0X381020000..0X381040000, the scaler's four windows (0X290000000..0X290008000 among them) but not its DART's, the ProRes engine's two and the audio roots' three; 0X308078000 and 0X3082A8000 are shared with nodes that stay. The words of the record render that one table, the read-back derives it again from the two trees and refuses a guest whose trees say otherwise (`GUEST_PROFILE_READBACK`), and `tools/test-sp11-m1-windows.py` parses both trees and fails for a seeded wrong window.

## 6. Limits

**The result of rung 7 (boot 27; OBSERVED, one unit, one boot; [SP11-STICK-LOG.md](SP11-STICK-LOG.md) section 25).** The profile `quiet` (43 nodes withdrawn by data) ran on the unit once, in the record's form of section 5. The scaler's stop of boot 26 (`A=0X291000004`) did not return, and no `S2_FAULT` of any address came in 120.185 s: neither of the record's readings of a stage-2 fault, THE PROFILE DID NOT TAKE (an `A=` in a withdrawn node's window) and THE STOP MOVED (an `A=` elsewhere), occurred. The kernel went through `bsd_init` to its last line, `Waiting on <dict ...>` for an `IOMedia` of content `Apple_HFS`, then 59 s of silence, and the monitor's own watchdog ended the run at the box's end (the record's class is RUNG 7 KERNEL WAITING; the wait is INFERRED to be the kernel's wait for a root device). Not known: whether the JPEG, encoder and display drivers started at all (none stopped the run), and which of the withdrawn nodes mattered beyond the scaler (UNKNOWN). The other seven profiles have no record text and no run.

The profile `quiet` let the stock kernel run past the stop that the default board reached (boot 27: OBSERVED, one boot); for any other profile it is UNKNOWN whether it does: the A16 comments say that the withdrawn drivers waited or panicked on absent hardware, which is INFERRED for the SP11. Withdrawing the display graph (`dcp`) leaves the panel as the console on boot_args.Video, which no profile touches (INFERRED from the A16 route). A withdrawn root whose register window has a model leaves the model in place (the models are those of the base board); nothing attaches to it. Each profile needs its own record, its own approval and a supervised hardware run.

## 7. quiet-rtc: the PMU's real-time clock (EXPERIMENTAL; hardware NOT RUN; admitted by rung 8's form only, K16)

**Why.** In boot 27's film (OBSERVED, one unit, one boot) the stock kernel prints `AppleARMRTC started!`, `AppleDialogSPMIPMURTC started!` and `Read RTC offset from leg_scrpad` at about t0 + 7 s, then about 1,000 lines of `parity error: parity_rcv=0x0000 parity_exp=0x000F` (and `0x001F`) and `_readRegs failed: e00002bc`, and never `AppleARMRTC registering service!`. `IORTC` is therefore not published and bsd_init's two 30 s waits for it expire (INFERRED, `files/stopsite-r8.md` and `files/result-boot27.md` of the session).

**What the stock kernel does (VERIFIED: read in the J700 26A428 kernelcache with `tools/kc-disas.py` and its helpers; derived facts only, no disassembly is kept).**
- `AppleSPMIController::extendedReadWriteCommand` accepts a read of n bytes only if bits 31:16 of the response's first FIFO word, under the mask 0xFF (the long forms, opcodes 0x30..0x3f) or 0xFFFF (the 16-byte forms), equal `(1 << n) - 1`, n being the length field of that same word plus one. That field is `parity_rcv` and `(1 << n) - 1` is `parity_exp`; a set bit is a byte received with good parity, a clear one prints `parity=BAD`, and the data words that follow are not looked at. So a model passes a read of n bytes, zero data included, by setting n flag bits in that word and returning ceil(n / 4) data words. Whether the wire parity is odd or even is not visible to the driver (UNKNOWN); the model computes none. The empty bus of the base board replies with the header and no flag, which is the film's `parity_rcv=0x0000` (`tools/test-spmi.c`).
- `AppleDialogSPMIPMURTC::handleStart` calls `_readConfiguration` and then `_readCurrentOffsetTicks`, which reads 4 bytes at `info-leg_scrpad` + 4 (0xf704) and 2 bytes at + 0x15 (0xf715) of the PMU's slave 14 and takes any value, zero included, as the clock offset. Only after both reads does it log `tick read!`, register its sysctls and return; `AppleARMRTC::start` then logs `registering service!` and publishes `IORTC`. A failed read returns before that. The driver waits for `AppleSMC` without a timeout only when the property or boot argument `rtc-offset-use-nvram` is set: the device tree has no such property on pmu-main and no boot argument of the stick sets it (VERIFIED by reading both).

**What binds it.** The model is the A16 chain's own (`compat/pmu-rtc.h`, `compat/device/device_rtc.c`, bound by `-bootfb-rtc` and everything built on it, `-xars-uniform` among them): the SPMI controller of `nub-spmi0` (base 0x308700000, the node of the J700 tree that the SP11's guest tree is) serves SID 14's upcounter at 0xf802 (six bytes, 32,768 Hz: the seed plus the guest's own counter) and the two offset fields, and refuses everything else with the empty bus's reply. The M1 monitor binary already holds it (VERIFIED by reading `profile-a/xnuboot.elf` of the pair, SHA-256 `c969aa1c...`: the controller's three routines are in it, with the clock's contract word and the 32,768 scaling; the scratch-pad code of `SNAP_SPMI_SCRATCH` is not, and the recipe `config/monitor-profile-sp11-m1.json` does not define it). So no monitor byte changes and the SNAPMON digest stays `bb34b970...`. The profile is the quiet profile with `spmi_boot` of that node set to `rtc=True` (`bind_rtc` of `probes/guestprofile_m1.py`; a clock at another node, at two or beside a split set is `GUEST_PROFILE_SPLIT`) and a seed.

**What changes in the guest (VERIFIED: `tools/test-sp11-m1-rtc-profile.py` `Guest`, with the kernelcache).** The device tree and the HANDOFF page are the quiet profile's byte for byte; in PARAMS, of the 120 device models, the one of `nub-spmi0` changes three words (kind 9 to 48, `config[3]` from 256 to the seed, `config[4]` from 256 to the contract) and no other word of the chunk. A stick has no host to sample UTC from, which the A16 route does at upload, so the seed is the constant `RTC_EPOCH_US` of the menu, 2026-11-20T00:00:00Z: a placeholder and not the unit's time, which the guest's calendar starts at when the monitor starts the model, so that a bundle regenerates byte for byte. A clock model with no seed is refused by the monitor at start; the builder refuses it before (`BUILT_SHAPE`) and the read-back refuses a bundle whose models are not the loader's own (`GUEST_PROFILE_READBACK`).

**What it would not change (INFERRED).** The PMU's SOCD container header (0x8800, five bytes), the LPM log and control words and the rest of the scratch pad (0xf700..0xf7ff beside the clock's two fields; 0x8f80..0x8fff) stay refused, so part of the parity noise remains; `SNAP_SPMI_SCRATCH` serves the last two windows and not 0x8800, and it is a compile gate of the monitor, hence a new SNAPMON digest, which this profile avoids. The root device is a separate wait. What the clock's start, once it succeeds, does to the rest of the boot is UNKNOWN: the later counter reads and a calendar that starts at a placeholder instant have been exercised on the A16 chain only, never on the unit.

**Prediction and falsifiers (INFERRED).** With the profile on rung 7's pair the clock driver should log `AppleARMRTC registering service!` about 7 s into the run, `IORTC` should be published, and bsd_init's burst and the wait on the root device should come about 52 to 60 s earlier than on boot 27. It is falsified by the absence of that line, by a parity error at 0xf704, 0xf715 or 0xf802, or by a stop in the SPMI controller's window (0x308700000). Rung 8's record (K16: rung 7's form with this profile, text in `tools/sp11_stick_bundle_panel_rung8.py`) is written for it; nothing of this has run. Evidence so far: `tools/test-pmu-rtc.c` (the model's packets, the stock kernel's parity predicate for the film's reads) and the suites of this change, host only.


## 8. quiet-rtc-acm: the credential manager in software mode, with a root (EXPERIMENTAL; hardware NOT RUN; admitted by rung 9's form only, K17)

`j700ap-26A428-m1-quiet-rtc-acm` is `quiet-rtc` (section 7: the 43 nodes withdrawn, the clock bound) plus ONE data-only layer, `acm_software_mode` (`compose(..., acm=True)`, `acm_of`, `ROOT_MENU`, `ROOT_PROFILES` in `probes/guestprofile_m1.py`), which makes the loader add the boot argument `acm_fastsim=1` to the guest's command line. The loader adds it only when it builds a RAM-disk root (`probes/xnuboot.py`), so a build of this profile without a root would have no effect of it and the stick builder refuses one (`GUEST_PROFILE_REFUSED`); and a root with any other profile is refused as well. The layer exists because the kernel's credential manager reads `acm_fastsim` and its strings include a timed wait for `AppleSEPManager`, which the argument is INFERRED to avoid (read on the host, `files/root-profile-note.md` of the session); that the unit's kernel needs it is UNKNOWN. It changes no node, no model and no word of PARAMS beyond what the loader writes for a root (the RAM disk's `/chosen` data, the trust cache's three words): rung 9's record (`tools/sp11_stick_bundle_panel_rung9.py`, text and classes) is written for it, and nothing of this has run. The read-back of section 4 is generalised: it compares the finished tree with `compose(name, sets, rtc, acm)` and names the layer that differs.
