# SP11 GPU study: UniXNU's Adreno stack as a reference for the X1-85 port

UniXNU is a public project that boots iOS and iPadOS on non-Apple ARM64 hardware through UEFI, and its README names GPU acceleration for the Adreno 740 of the SM8550 as part of it [VERIFIED U207 U208]. It ships a kernel GPU service, a Metal plug-in, an AIR-to-NIR kit and PM4 and firmware kits. The A740 and the Adreno X1-85 of the Surface Pro 11 are both a7xx parts, and Linux files both in the same gen2 family [VERIFIED U213 U214], so a second, independent a7xx stack is worth reading for the SP11 port described in [SURFACE-PRO-11.md](SURFACE-PRO-11.md). The X1-85 side (catalog entry, `CP_PROTECT`, GMU, UBWC, speed bins) is in [SP11-GPU-A7XX-STUDY.md](SP11-GPU-A7XX-STUDY.md); this document adds what UniXNU's stack does, what its authors report having measured, and where it differs from ours.

This study does not recommend replacing any component of ours; the operator decides.

Nothing was built or run, no device was touched and no UniXNU code or prose is copied: every claim paraphrases a cited line and carries an evidence label and register ids ([section 0](#0-how-to-read-this-document)). Design intent and hardware results are kept apart (section 2.11). Hardware status: NOT RUN.

## Key findings

1. **Shape.** UniXNU's GPU path is an EL1 Darwin kernel service with Turnip in userland: Metal reaches the AdrenoMetal plug-in, which builds on metal2vulkan and hands SPIR-V to Turnip, and a Darwin kernel-mode driver passes Turnip's command streams to the Adreno740 kernel service [VERIFIED U26 U21 U34 U183]. The kernel is entered at EL1 [VERIFIED U186]. Ours cuts the work differently: an EL0 plug-in, an EL1 kext and an EL2 monitor that checks command streams and owns the GPU SMMU [VERIFIED U138 U139 U135 U194]. A resident hypervisor was observed keeping some SMMU context banks on the donor board [OBSERVED U187].
2. **Compilers.** AirNir is an offline kit: its front end takes straight-line AIR only, its backend rejects any non-gen-7 id and its result records no GPU execution [VERIFIED U32 U44 U45 U46]. Run-time translation happens elsewhere [VERIFIED U33]: AIR goes through metal2vulkan to SPIR-V, Turnip compiles that, and the shader cache holds Turnip's ir3 output [VERIFIED U183 U188]. Ours is the air2ir3 runtime [VERIFIED U136]. Both Mesa pins list the wildcard ids `0xffff43050a01` and `0xffff43050c01` in one a7xx gen2 table row, so Mesa treats the X1-85 as a sibling of the A740 [VERIFIED U128 U130].
3. **12 + 5 + 2 = 19.** For the A740 family Linux makes twelve and five RSC writes and two PDC writes while bringing the GMU up, and UniXNU's GMU generator insists on exactly 19 [VERIFIED U107 U108 U109 U79 U81 U82]. Linux returns before this code for a8xx parts [VERIFIED U105]. That the X1-85 needs the same 19 follows only from both entries being gen2 under one family test [INFERRED U213 U214 U110 U215]; X8a and plan item F2 must settle it.
4. **IFPC is the main power-state difference.** UniXNU runs the A740 with IFPC off and packs a sixteen-register power-up list with no IFPC and no dynamic entries [VERIFIED U52 U176 U177]. Linux's X1-85 entry sets the IFPC quirk and names the IFPC register list, which Linux's own note says applies to the X185 and A750, and an a7xx dynamic list also exists [VERIFIED U116 U216 U120 U190 U121]. Whether the X1-85 needs any of them for a first bring-up is UNKNOWN [UNKNOWN] (Q02).
5. **ZAP lives only in the donor-board probe.** The probe loads a zap shader through SMC calls with PAS id 13 and says the secure-video trust register is therefore never written [VERIFIED U88 U89]; the zap stage is a boot argument and the probe is unvalidated by its own header [EXPERIMENTAL U90 U92]. The platform kit's cold-start header says that its success does not cover the zap shader [VERIFIED U87], and a scan of the kernel service's tree and of the PM4, firmware, SMMU and platform kit trees finds the word only in that comment [INFERRED U87]. Linux's X1-85 entry names no zap image while the A740 entry does, the upstream EL2 overlay disables the zap node, and Linux's no-zap branch writes the trust register itself [VERIFIED U122 U223 U224]. SP11 is therefore expected to be zap-less like our A16 flow [INFERRED U115 U223 U224 U230], and UniXNU's flow gives no evidence for that case (Q03).
6. **Rings and preemption.** The service runs two rings with a priority map, an aging rule and preemption selected by `gpu-preempt=2`; the preemption record is 4192 KiB for both the A740 and the X1-85 entries in Linux [VERIFIED U28 U29 U31 U63 U70 U124 U126]. Our monitor drives one context with no preemption [VERIFIED U132].
7. **No PM4 content validator was found.** The service checks a submission's buffer list against the live address space, not the PM4 stream, and the PM4 kit's planner decodes structure and authorizes nothing [VERIFIED U67 U182]. The generated `CP_PROTECT` table has 46 entries and the donor-board probe writes it [VERIFIED U75 U220]; a scan of the eight pinned source trees finds no other reader [INFERRED U75 U74 U220 U264]. What protects the service path beyond per-client address spaces [VERIFIED U27] is UNKNOWN [UNKNOWN] (Q08).
8. **The hardware evidence is thin.** Records are single units: sheng primed 280 of 280 shader libraries, boots the image and accepts touch, had an idle panic that was fixed, and later booted a responsive desktop [OBSERVED U140 U141 U142]; the repository's own report lists frame pacing and repeated preemption as pending [VERIFIED U147 U246].
9. **Licences differ by repository.** The main, board, platform-kit and firmware-kit repositories are BSD-2-Clause-Patent, not MIT [VERIFIED U01 U02 U03 U04 U05]; the kernel service, plug-in, AirNir, PM4 kit and SMMU kit are MIT [VERIFIED U06 U07 U08 U09 U10]. The MIT plug-in links an archive built from metal2vulkan, which is GPL-2.0-or-later or LGPL-3.0-or-later [VERIFIED U12 U14].
10. **The OS ABI differs.** The kernel service is pinned to an iPadOS 17.7.11 build; the newer profiles name a macOS 27.3 and an iPadOS 27.0.1 build and run an older XNU because no Darwin 26 XNU source exists [VERIFIED U40 U41 U42 U43]. Ours targets macOS 27 build 26A428 [VERIFIED U206]. UniXNU's user-client, plug-in and QuartzCore assumptions therefore cannot be assumed for 26A428 [INFERRED U40 U55 U56 U97 U206].
11. **UBWC and GPUCC constants line up; one flag set does not.** Linux gives SM8550 and X1E80100 the same UBWC table entry and the same GPUCC base and GDSC offsets as UniXNU's board header, but the X1E80100 GX domain flags add the AON and SW resets that the SM8550 ones lack and omit the fast-forward retention flag that the SM8550 ones carry [VERIFIED U155 U156 U159 U160 U85 U86 U161 U162 U163 U164]. The effect on X1-85 GX bring-up is UNKNOWN [UNKNOWN] (Q05).
12. **Hardware init is board code.** The kernel service takes its GPU restart from a hook the board installs [VERIFIED U244 U245]; the donor-board probe, whose hardware init ports the A740 branches only, writes the generated protect table [VERIFIED U220 U221], and a scan of the eight pinned source trees finds no other reader of the protect and clock-gating tables [INFERRED U75 U74 U220 U264].
13. **Reuse is cite-only by default.** Section 6 states what adopting an MIT component would involve (files, changes, notices, ownership, equivalence tests, cutover and retirement conditions) under our rules [VERIFIED U197 U198 U227]. This study does not recommend replacing any component of ours; the operator decides.

## 1. Answers to the seven questions

**Question 1: what is the stack?** A kernel service, userland translation and five small kits. The Adreno740 service owns GPU memory mappings, command submission, fences and CP and GMU initialisation, and the board supplies firmware, power votes and display integration [VERIFIED U248]. Turnip is the userland driver behind a Darwin kernel-mode driver [VERIFIED U26 U21]; the AdrenoMetal plug-in builds on metal2vulkan [VERIFIED U34] and AirNir is offline [VERIFIED U32]. The kits cover PM4 packet encoding, GMU firmware loading with the HFI protocol, native 4 KiB SMMUv2 tables and, as board code supplied by the SoC repository, the GMU, the GPU SMMU and the RPMh command database [VERIFIED U36 U249 U252 U250 U251]. Section 2 covers bring-up, rings and preemption, memory, power, firmware inputs, UBWC, `CP_PROTECT` and diagnostics. Design intent is kept apart from results in section 2.11: the OBSERVED records are single-unit statements by the authors and none is reproduced here [OBSERVED U140 U141 U142].

**Question 2: how does it compare layer by layer with ours?** Section 3 tabulates it. The stacks cut at different places. UniXNU keeps address-space setup, submission, rings, preemption and hang recovery in one EL1 service and checks a submission's buffer list against the live address space [VERIFIED U248 U63 U67 U245]; ours checks every IB against protect tables at EL2, writes the ring there and keeps the encoders and the compiler in userland [VERIFIED U135 U194 U138 U136]. Chip-specific material (register offsets, tables, GMU sequences) may carry to the X1-85 once re-verified there; the OS-ABI-specific material (user-client class, plug-in open type, ABI version, QuartzCore patching) is tied to a build of Darwin [VERIFIED U55 U56 U57 U97].

**Question 3: what changes from the A740 to the X1-85?** Section 4 tabulates it. Both Linux entries are gen2 and share the protect table, the clock-gating table, 3 MiB of GMEM and a 4192 KiB preemption record [VERIFIED U213 U214 U217 U218 U219 U165 U166 U124 U126]. They differ in chip id (`0x43050a01` against `0x43050c01`), GMU chip-id word (`0x7020100` against `0x7050001`), GMU image (`gmu_gen70200.bin` against `gen70500_gmu.bin`) and in the X1-85's IFPC quirk [VERIFIED U112 U114 U123 U125 U113 U115 U116]. linux-firmware lists the X1-85 images `gen70500_sqe.fw` at 1.62, `gen70500_gmu.bin` at 4.03.11 and `gen70500_zap.mbn` at 0.15 [VERIFIED U131]. UniXNU's GMU kit hard-checks the A740's chip id and image length and writes the A740's chip-id word, so its generated constants would have to be regenerated for the X1-85 [VERIFIED U294 U295 U296 U297] [INFERRED U294 U295 U296 U114 U125 U131]. SM8550 and X1E80100 share one UBWC table entry [VERIFIED U155 U156]. UniXNU contains no X1-85 DVFS levels and nothing about speed bins; both stay UNKNOWN here [UNKNOWN] (a7xx study §2.12; X8a).

**Question 4: who powers the GPU, loads the firmware and owns RPMh and the GPU SMMU?** In UniXNU's flow the kernel is entered at EL1 [VERIFIED U186] on a donor board where a resident hypervisor was observed keeping some SMMU context banks [OBSERVED U187]. The kernel service takes the GMU and microcode images from images embedded at link time through weak defaults [VERIFIED U24]. The board probe enables the CX power domain, builds the GMU's and the GPU's own SMMU contexts and asks the GMU to power GX [VERIFIED U238 U240 U263 U239]; the zap shader goes through SMC calls with PAS id 13, in the probe only [VERIFIED U88 U89]. Which agent owns RPMh votes and the GPU SMMU where a hypervisor holds some banks is not established by anything read [UNKNOWN] (Q04). In the plan, UEFI runs at EL1 under Gunyah and EL2 is reached through slbounce [VERIFIED U256]; clocks, GDSCs, RPMh votes, the GMU and the firmware load then belong to EL2 code, plan item F2 [VERIFIED U229], as on the A16, where q1n1 powers the GPU before the guest and the monitor owns the GPU SMMU [VERIFIED U195 U194]. The upstream EL2 overlay's comment that Linux can zap the GPU itself is verbatim in `x1-el2.dtso:14-17` and in a7xx study §2.7 [VERIFIED U223], and the plan's N2 row carries it paraphrased [VERIFIED U230]. ### 2.2 Kernel service and bring-up

The service's own start path is an opt-in sequence. Its header says that board power, GMU boot and SMMU context programming are not implemented for Darwin yet and that start maps the first register window and stops [VERIFIED U48]. The sequence that goes further is selected by a boot argument: with the opt-in alone the SMMU window is only read, and with the bank, ASID, stream-id and slot arguments as well it programs the SMMU, prepares a context bank, attaches the stream and maps the GMU payloads [EXPERIMENTAL U49]. The comment on the opt-in warns against running it before a read-only observation shows the GPU SMMU powered and writable, because the apps SMMU on the donor board is hypervisor-managed and the GPU SMMU has not been shown to differ [VERIFIED U50]. The code from line 343 to line 510 is that sequence and ends by marking the core ready [VERIFIED U51].

| Step in the service's own start path | What the source does | Evidence |
| --- | --- | --- |
| GMU image | Validates the embedded image against a fixed size and SHA-256 when the build carries generated rules. The embedded firmware images are weak definitions that the firmware archive replaces, and a zero length is refused with no SQE upload. | [VERIFIED U25 U24] |
| Command database | Needs a boot argument naming the database version. The parser reads an immutable CPU-readable snapshot, maps nothing and does not verify provenance, integrity or authenticity; its checksum is unused. | [VERIFIED U241 U242 U243] |
| Power policy | Leaves IFPC off: the power-up list carries no IFPC restore registers and write-pointer writes are not fenced, so a collapse between frames would lose the CP's state. | [VERIFIED U52] |
| GMU cold start | Calls the platform kit's cold start with the assembled configuration, the start-up profile and four limits, and logs the status, the readiness observed and the protocol stage. | [VERIFIED U53] |
| Ring and SQE step | Refused after the cold start while the service's GPU-context flag is false. | [VERIFIED U267] |
| Power-up list, then CP | Builds the A740 power-up list into a mapped 4 KiB page, starts the CP, waits for the start fence and attaches the interrupt block. | [VERIFIED U178 U179] |
| Core ready and publish | Marks the core ready, and registers the service when the ready flag is set. | [VERIFIED U51 U54] |

At the pin the sequence cannot reach its own publish step. The flag that guards the ring and SQE step is declared false in the service's start path [VERIFIED U266] and the step is refused while it is false [VERIFIED U267]. The ready flag is set in one place only, inside that guarded step [VERIFIED U275], and start ends by refusing to publish, stopping and returning false whenever the ready flag is unset [VERIFIED U274]. A scan of every pinned clone finds no other assignment to the flag, so the service's own start path cannot publish [INFERRED U266 U267 U275 U274]; this is an absence result of a text scan, not a run.

The published service on the donor board therefore comes from a second path. The publish file calls itself the IOKit surface for an already-running GPU context: board code brings the GPU up and hands over the live VM, submit object, ring, clock and optional timer, and one service is published [VERIFIED U283]; its entry point takes a VM, submit object and ring that board code has already attached to that context [VERIFIED U268]. The only caller found is the donor-board probe, which hands over its own VM, submit object and ring [VERIFIED U271] right after asking the secure world to open the CP aperture [VERIFIED U273 U272]. The probe reaches that point only in the branch taken after its first scratch write through the GPU's own context landed and the fence signalled [VERIFIED U269]; in the same branch the zap step runs, staged by a boot argument [EXPERIMENTAL U90], and the board installs the GPU restart hook before the service is published [VERIFIED U270]. That the probe is the only caller is an absence result [INFERRED U271 U268], and the consequence is that the service seen publishing on the donor board was handed over by the probe, not produced by the service's own start path [INFERRED U266 U267 U271 U274 U275]. Which revision, boot arguments and path produced each reported run is not recorded in anything read [UNKNOWN] (Q10; operator).

Hardware init and recovery are board code too. The service takes its GPU restart, a reset plus hardware init, from a hook the board installs [VERIFIED U244], and with no hook a hang is only counted [VERIFIED U245]. The hang check is modelled on msm's and only the client whose submission hung sees its device lost [VERIFIED U66 U279]. The probe's restart resets the GPU registers while the GMU keeps running, because the GMU kit has no stop and warm-boot path [VERIFIED U225]; its hardware-init list covers the GBIF halt release, the SECVID TSB, clock gating, QoS, UCHE, AHB, hang detect, CP protect, APRIV and the interrupt mask [VERIFIED U264].

### 2.3 GMU, HFI, RSC and power

The firmware kit's HFI part follows strict rules. It is initialised while the GMU is stopped and never resets a running queue [VERIFIED U200]; one command may be outstanding and a failed notify poisons the session [VERIFIED U199]; the caller owns an exclusive 16 KiB extent mapped with four native 4 KiB pages, barriers are real outer-shareable barriers and acknowledgements are never faked [VERIFIED U77]. The start-up stages run in the order performance levels, bandwidth, ACD enable, ACD table, IFPC, core start, start and complete [VERIFIED U180], over the modern A6xx and A7xx wire profile; legacy and A8xx table formats are excluded [VERIFIED U78].

The platform kit's cold start is not a power, clock, SMMU-ownership or boot entry point. The caller must already hold the power domains, the verified A740 boot clocks, the RPMh and interconnect votes, exclusive ownership and native 4 KiB GMU mappings, with the GMU held in reset and the RSC idle; the function does not read silicon identity, checks the complete firmware hash before any register write and treats a protocol failure after the load attempts as permanently poisoning the device [VERIFIED U80]. After its reset, idle and stale-ready checks it writes every entry of the generated RSC and PDC setup table in order and issues a barrier before it touches the GMU interface registers [VERIFIED U79]. Success covers the firmware start-up exchanges, not SQE, ZAP or GPU initialisation, shader execution, submission or presentation [VERIFIED U87].

The kit is also pinned to the A740 by generated constants. Its argument check refuses a chip id other than one generated constant and a firmware length other than a generated one, and requires five GMU memory areas of fixed sizes [VERIFIED U294 U298]; the generator writes the A740's chip id as that constant and takes the GMU chip-id word and the firmware length and hash from the A740's catalog record and GMU image pin [VERIFIED U295 U296]; the cold start writes the word to a GMU register [VERIFIED U297]. None of these values is the X1-85's (section 4).

The setup table is generated from Linux's GMU file, and its size is a hard check:

### 2.5 Memory and the SMMU

Each connection of a user process has its own address space and queue range; the GPU uses 4 KiB SMMU pages, owned buffers use system memory, imported pages keep their owners and an unmap invalidates the affected translations [VERIFIED U27 U232 U277]. The page tables come from the ArmSmmu4K kit [VERIFIED U252].

### 2.10 Diagnostics

UniXNU's diagnostics are driven by boot arguments and are bounded. One line of boot arguments enables a boot log, GPU tracing, GPU performance counters and a diagnostic export; the export runs once at the selected boot-log time, the switches do not schedule a reboot, and normal builds leave GPU tracing disabled [VERIFIED U39]. The donor-board power probe is default-off and staged by a numeric boot argument, and its own header calls it an observation of power and clock state [VERIFIED U258]; its zap step is staged the same way [EXPERIMENTAL U90]. The plug-in's published mode needs a marker file, so a build without it never takes the GPU path [VERIFIED U95]. The scheduling host test, with address and undefined-behaviour sanitizers, is listed as passing for packet encoding, GMEM, keepalive, pending and timeout states, per-ring context, FIFO order, fence-history rollover and the CPU-table fallback [OBSERVED U146].

The porting guide says what to collect for another board (registers, interrupts, SMMU contexts and stream ids, firmware, power domains, clock and voltage levels, interconnect votes, RAM reservations and scanout layout) [VERIFIED U235]. Its expected results are GMU startup and an HFI response before any command is submitted [VERIFIED U236], and then CP initialization, ring progress and fence completion with bounded work [VERIFIED U237]; a new GPU generation needs its own kernel backend and compiler support before a frontend is chosen [VERIFIED U234]. Those exits line up with the plan's X8a and X8b gates [VERIFIED U231] (section 8). Our rules have the same shape: critical paths must not block on console I/O or host RPC, and diagnostics use bounded asynchronous buffers [VERIFIED U209].

## Appendix A. Method notes

**Method.** The study reads read-only clones of nine UniXNU repositories at the commits listed in Appendix B, plus the pinned Linux, Mesa and firmware trees named there. Nothing was built, run or loaded and no hardware was touched. A register row in Appendix C gives a citation key, a path and line range, a token that the pinned text must contain, and a paraphrase in this study's own words; no UniXNU code or prose is copied and quotes are short identifiers.

**Local audit.** To reproduce the checks, clone each repository with `git clone https://github.com/UniXNU/<name> build/ref/unixnu/<name>`, check out its Appendix B commit, and put the Linux, Mesa and firmware trees at their Appendix B pins under `build/ref/`, which is git-ignored. `python3 tools/test-sp11-gpu-unixnu.py` then checks each row against its pinned file and prints how many rows it checked and skipped. With no checkouts present it checks the structure of the study and says what it skipped. The variables `SP11_UNIXNU_REFS`, `SP11_LINUX_TREE`, `SP11_MESA_TREE`, `SP11_FIRMWARE_TREE` and `SP11_MESA_UNIXNU_TREE` point the audit at other copies of the trees.

**What the test checks.** First, the structure: the SPDX and study-only lines, ASCII-only text, the headings in order, a label tag with register ids on every table row of sections 1 to 8, every register id cited, and every cited id present with the label the register gives it. Second, the register: with all trees present 308 of 313 rows are checked and 5 skipped, namely the rows whose source is not cloned (the metal2vulkan and GitHub-API rows). Third, 14 derived-fact checks that recompute headline facts from the pinned trees, such as the 12 + 5 + 2 = 19 list, the firmware names, the table sizes, the power-up list sizes, where the IFPC quirk is set, the consumer and zap-mention scans, the never-set GPU-context flag, the single publish caller, the Mesa rows, the count of translator patches and the three ABI data files. Fourth, 16 in-process mutants of the text, each of which the checks must reject.

**Dated observations.** The rows labelled OBSERVED for licences come from a GitHub API query of the public repositories on 2026-11-10. The metal2vulkan licence was read from the project's raw file because that repository was not cloned.

**Dropped claim.** One claim in UniXNU's device notes, that a stress workload ran stably, could not be located in the pinned text and was dropped.

**Not covered.** Our kext and plug-in repositories are submodules that are not checked out in the tree this study was written in, so our side of every comparison is read from `ARCHITECTURE.md`, `AGENTS.md` and `compat/` only (Q16).
