# SP11 X2 EL2 tests, third version: T06 reads only the NVMe's own PCIe root

**Hardware status: the `declared` variant ran once on the unit (2026-11-15, one unit, one boot): T06 PASS.
The `hardware` variant is NOT RUN.** Sections 1 to 12 were written before that run. Where they say what the unit will
show, that is a prediction from the code and from QEMU/EDK2 runs, never an observation; the only later edits to them
are short notes that say what the run showed, most of them pointing at [section 13](#13-the-run-on-the-unit-2026-11-15),
which compares the prediction with what the unit showed. Evidence labels: VERIFIED (reproduced
by a test in this repository), OBSERVED (read on the unit; the source is named), INFERRED (follows
from other results), EXPERIMENTAL (written and host- or emulator-tested only), UNIMPLEMENTED,
UNKNOWN. A host or QEMU result is a model result and is labelled as one.

Related: [SP11-X2-TESTS.md](SP11-X2-TESTS.md) (operator guide, runs 1 to 7),
[../probes/uefi/tests/README.md](../probes/uefi/tests/README.md) (design),
[SP11-NVME-WINDOW.md](SP11-NVME-WINDOW.md) (what the NVMe takeover needs from T06: rows D2 to D4, D8, D15).

## 1. Why a third version

The second version (build `E5BF1A6BD94C`, the `declared` variant, run on the unit) walked every ECAM
window the MCFG lists, in table order, and the machine stopped on the third segment.

| Fact | Label | Source |
| --- | --- | --- |
| T03, T04, T05 and T09 PASS; K1 stays GO; the REGIME row says `E2H=0 TGE=1` | OBSERVED | the v2 photographs |
| T06's last footer was `T06 ECAM 0740000000`: the MCFG entry of segment 3, base 0x740000000, buses 0 to 1 | OBSERVED | operator photograph |
| The read never returned and the board rebooted by itself | OBSERVED (the reboot, operator report) | |
| That it was a hang followed by a watchdog reset | INFERRED | no other signal exists |
| Why segment 3 does not answer (a root complex whose power, clock, PHY or link state nobody set up or kept) | UNKNOWN; the hypothesis is INFERRED and untested | |
| The MCFG holds eight entries (below) and the DSDT has eight PCI roots with `_SEG` = `_UID` = 0 to 7 | OBSERVED | the dumped tables; plain numbers only, no table bytes are kept here |
| The firmware's NVMe block device path is `PcieRoot(0x6)/Pci(0x0,0x0)/Pci(0x0,0x0)/NVMe(...)` | OBSERVED | the firmware's device path |
| So the NVMe is behind segment 6, ECAM 0x70000000 | INFERRED, from `_UID` = `_SEG`, when this was written; OBSERVED on 2026-11-15 (section 13). The new T06 checks that claim at run time instead of trusting it | |

The operator's decision: **"NVMe at EL2: read only the NVMe's own PCIe root."** The rule of this version
is that T06 never reads an ECAM window of a root complex the firmware itself did not use for its NVMe.

## 2. What changed, and what did not

Changed:

1. **A record of the firmware's own PCI I/O view, taken before ExitBootServices** (`pciio.c`, `pciio.h`).
   Read-only; section 3.
2. **T06 reads only the segment of the firmware's NVMe**, cross-checks what EL2 sees against that record,
   and reads seven NVMe registers next to the firmware's values (`t_pcie.c`); section 4.
3. **A photograph pause of 8 s** before the first read of an ECAM window and again before the first read of
   the NVMe BAR0 window (`hook.c`, `suite.h`); section 5.
4. **`pciio.txt`** is a new file in the stick's dump run directory, and the console gets one new line,
   `SP11X2 PCIIO STATE=<state> HANDLES=<n> NVME=<n>`.
5. Tests, a source audit for the PCI I/O module and 46 seeded-bug mutants (section 10).

Not changed: T01 to T05 and T07 to T09, the K1 logic, the NV2 record, the REGIME row, the single range the
`declared` variant declares (the image itself), the post-bounce order (T06 last), the image names
(`TESTS.EFI`, `TESTS-DECL.EFI`; the stager is untouched). T03 still does not read `CNTPOFF_EL2` (a read of it
at EL2 never returned on this unit: INFERRED from the line count of boot 4 of the payload runner).

## 3. Before ExitBootServices: what the firmware itself knows

`tests_pciio_collect` runs in phase A, before the memory-map loop that ends in ExitBootServices, and
frees everything it allocates before it returns (a pool list from `LocateHandleBuffer`). The table
(`g_pciio`, at most 64 functions) lives in the image's `.bss`, which the declared range already covers.

**Allowed calls.** `LocateHandleBuffer(ByProtocol, EFI_PCI_IO_PROTOCOL_GUID)`, `HandleProtocol` (PCI I/O and
device path), `FreePool`, and on each PCI I/O instance `GetLocation`, 32-bit `Pci.Read` and 32-bit `Mem.Read`.
Every other member of the protocol is declared as an untyped placeholder, so a call to it does not compile,
and `_Static_assert` pins all 20 member offsets and the 160-byte size to the UEFI 2.10 order (a swapped slot
would turn a read into `Pci.Write` or `SetBarAttributes` with no diagnostic). The host tests give a fake
protocol whose every other member fails the test when called; `host/audit.py` (`audit_pciio_access`) fails the
suite if the module names a write, `Io.*`, `Map`, `Unmap`, `AllocateBuffer`, `Flush`, `Attributes` or
`SetBarAttributes`, calls a boot service other than the three above, or if a member offset or a typed member of
the structure changes.

**Reads.** Per function: config offsets 0x00 (ids), 0x04 (command, status), 0x08 (class code, revision),
0x0C (header type), then BAR0 to BAR5 (0x10 to 0x24) for an endpoint, or BAR0, BAR1 and 0x18 (primary,
secondary, subordinate bus) for a header type 1 bridge. BARs are decoded (32- and 64-bit memory BARs) and
never sized: nothing is written. From the handle's device path only the first node is read, and only if it
is a 12-byte ACPI node: HID and UID, shown as the Shell shows them (`PcieRoot(0x6)`).
For a function of class 0x010802 (NVMe) with an assigned memory BAR0 and memory decode on, `Mem.Read` of BAR 0
reads CAP (offsets 0x00 and 0x04), VS (0x08), CC (0x14), CSTS (0x1C), AQA (0x24), ASQ (0x28, 0x2C) and ACQ
(0x30, 0x34), and nothing else. With decode off the controller is not read (`regs=DECODE OFF`).

**Failures are recorded, not hidden.** `NO PROTOCOL`, `LOCATE FAILED`, `NO BOOT SERVICES` or no NVMe function
give an empty NVMe list, and an empty list makes T06 NOT-RUN with nothing touched: there is no blind scan.

**The file.** `SP11DUMP/RUNnn/pciio.txt` (`# SP11X2 pciio v1`) holds the header (`build=`, `kind=`, `state=`,
counts), one `pci` line per function and one `nvme` line with the seven registers. The stick writer puts it
last in the one stick call, after `x2-results.txt` and the NV2 record, so a file that already exists on the
stick can only stop `pciio.txt`, never the K1 record. It is decoded by an independent oracle
(`host/pciio_text.py`) in the tests. The dump now has one file more (QEMU: `FILES=4` became `FILES=5`).
Where the platform is not yet at EL2 before ExitBootServices (the Surface Pro 11), phase A runs no test but
still takes the record and writes `pciio.txt`.

## 4. T06 at EL2

A segment is read only if **all** of these hold, in this order (`justify` in `t_pcie.c`); a failed one is
shown as `NVMEk SKIP: <reason>`:

1. the firmware's record of the function is complete (located, config read);
2. the device path starts with an ACPI root whose HID is PNP0A08 (or PNP0A03; QEMU/EDK2 uses PciRoot), and its
   UID is available;
3. **the root UID equals the segment** (double evidence with `_UID` = `_SEG`; INFERRED for the unit);
4. the MCFG parsed without losing entries, **exactly one entry carries that segment**, and it starts at bus 0.

The window is then validated as every device window is (unchanged): base aligned to 1 MiB, the UEFI memory
map's verdict (`MAP MMIO=<n> UNLISTED=<m> REFUSED=<k>`; strict or default policy), the allow-list, and
`TESTS_PA_LIMIT` (1 << 52). **There is no 2^36 rule**: the code has none and a test pins that a window above
2^36 is read like any other. Only then is it put on the allow-list, which is what makes any other MCFG window
unreadable whatever the walk does. Row `SCANNED SEGMENTS=<n> MCFG=<m>` says how many were read of how many exist.

**What is read in a window** is unchanged: bus 0 device 0 (ids, class, header type, command; the PCI Express
link capability and `LINK GEN<g> X<w> DLLLA=<0|1>`); for a bridge, its bus numbers and windows, then device 0
of the secondary bus (ids, class, command, BAR0/BAR1). A non-bridge at device 0 also gets devices 1 to 7 read.
The NVMe registers are read only if the endpoint **is the function the firmware recorded** (ids, class and BAR0
base equal), memory decode is on at the endpoint and at the bridge, BAR0 is 4 KiB aligned and inside the
window the bridge forwards, and the 4 KiB window passes the allow-list (`NVME BAR0`).

**Cross-check rows.** `MATCHES FIRMWARE VIEW=YES|NO`, `CAP VS EQUAL=YES|NO|N/A`, then `CAP`, `VS`, `CC`,
`CSTS`, `AQA`, `ASQ`, `ACQ` each with `PRE=` (the firmware, before ExitBootServices) and `EL2=`. CAP and VS
are constant registers and must be equal. CC, CSTS, AQA, ASQ and ACQ may differ: what the firmware's
ExitBootServices handling did to them is the information, so a difference is **not** a failure.

**Verdict** (first rule that applies):

| Situation | Verdict | `WHY:` row |
| --- | --- | --- |
| nothing justified, nothing refused, photograph fine | NOT-RUN | `NO SEGMENT WAS JUSTIFIED` (or the two rows `NO FIRMWARE NVME: NOTHING TOUCHED` + `PCI I/O: <why>`) |
| nothing read because the photograph wait failed, or a window was refused | UNKNOWN | `PHOTOGRAPH WAIT FAILED` / `A WINDOW WAS REFUSED` |
| a guarded read faulted | UNKNOWN | `A READ FAULTED` |
| no endpoint behind the root port at EL2 | FAIL | `NO ENDPOINT AT EL2` |
| ids, class or BAR0 differ from the firmware's | FAIL | `IDS OR BAR0 DIFFER FROM FW` |
| CAP or VS differ from the firmware's | FAIL | `CAP OR VS DIFFER FROM FW` |
| the registers were not (all) read, or the firmware's could not be | UNKNOWN | `NVME REGISTERS NOT READ` |
| a firmware NVMe was not checked (a second function in a scanned segment, an unjustified function, a window of another target refused) | UNKNOWN | `NOT EVERY FW NVME CHECKED` |
| otherwise | **PASS** | none |

Two NVMe functions on two segments are both scanned and nothing else is; the later one gets one row
(`SEG<n> VIEW=YES CAPVS=OK`). The unjustified ones (UID differs, segment not in the MCFG, a segment twice, a
start bus other than 0) are skipped with a row and count against PASS, so a partly checked machine cannot pass.

## 5. The photograph pause

Boot 3 nearly lost its page: the board resets within seconds of a stalled read (about 12 s after the T03
freezes of runs 1 to 5, operator report). So the page is drawn, and held, **before** each read that may not return.

* Before the first read of an ECAM window: the finished page of T01 to T05 and T07 to T09 plus the rows T06
  has decided so far (`FW NVME FUNCTIONS`, `NVMEk SEG=.. UID=..`, `SCANNED SEGMENTS=..`) is drawn with the
  footer `PHOTO NOW: T06 ECAM <10 hex> IN 8 S`, counting down once a second, then the plain footer
  `T06 ECAM <10 hex>`, then the read. Before the first read of the NVMe BAR0 window the same with
  `T06 NVME <10 hex>`. Later windows only name their address in the footer.
* The wait is `TESTS_PHOTOGRAPH_WAIT_SECONDS` (8) in `suite.h`, its one definition, with one call site in
  `t_pcie.c`; a test pins both, and a fake counter proves the wait is made before the first access to the
  window and that nothing is waited for when T06 has nothing to touch.
* The wait polls `CNTPCT_EL0`. No sleep primitive, no interrupt, no firmware call. Frequency: `CNTFRQ_EL0`
  if it lies within 1 MHz to 1 GHz, else 19.2 MHz (the unit's value, OBSERVED in T03). q1n1's page polls
  `CNTPCT_EL0` continuously at EL2 on this unit without a reset (OBSERVED, [SP11-X2-TESTS.md](SP11-X2-TESTS.md),
  "Update, 2026-11-12"), so polling the counter is not the reset trigger. (That page was in the VHE state; a plain q1n1
  page in the de-VHE state was alive at `UPTIME 123 S`, and after the `cpuon` payload the board restarted by itself in
  two of three boots, cause and times UNKNOWN: [SP11-STICK-LOG.md](SP11-STICK-LOG.md) section 14. The two photograph
  pauses of run 7 polled the counter, 8 s each by design, and did not reset.)
* **Fail closed.** If the wait cannot be made, nothing further is read: the row says
  `PHOTOGRAPH WAIT FAILED: CODE=<n>` (1 refused: no layout or an out-of-range length; 2 the counter went
  back by more than 1 s; 3 no progress for 2^24 polls) and the verdict is UNKNOWN.
* **A real finding while testing.** Under heavy host load the QEMU run failed this wait: a counter read came
  back less than 1 ms behind the highest value seen (OBSERVED under QEMU/TCG; the reads are `mrs` without an
  ISB, so on hardware reads may also be reordered, INFERRED). A strict "never backwards" rule would have
  refused every read for an effect no one cares about, so time is now the highest value seen, small backward
  steps are ignored and only a step of more than 1 s fails (5 of 5 failures before the change, 4 of 4 passes
  under load after it).
* The row `SCANNED SEGMENTS=<n>` is printed before the first read, so a photograph taken during the wait shows
  it, and is rewritten after the walk if fewer windows were read (a failed wait gives `SCANNED SEGMENTS=0`).

**Wall-clock cost.** The two 8 s waits are the only deliberate delays. T06 adds **16 s** when it reads an
ECAM window and the NVMe BAR0 (the expected case), **8 s** when it reads an ECAM window and not the BAR0
(refused, view differs, decode off), and **0 s** when it has nothing to touch (no extra wait, no extra redraw).
QEMU, model run: each countdown measured about 8.1 s. Not counted and not measured on hardware: the pre-ExitBootServices
collection (at most 64 functions, about a dozen config reads each, plus ten register dwords per NVMe) and the page redraw
(once per wait and one footer redraw per second).

## 8. What each outcome means for the NVMe host

`nvmeh_adopt` (`compat/nvme-host.c`) accepts a controller only if CC.EN is 1, CSTS.RDY is 1, CSTS.CFS is 0,
AQA is `(31 << 16) | 31`, and ASQ and ACQ are `dma_base + 0x0000` and `dma_base + 0x1000`, the monitor's own
queue memory. A firmware queue can not satisfy the last two (INFERRED: it lives in firmware memory), so the
monitor adopts only a controller that q1n1's takeover has reset and given its own queues (CC.SHN, CC.EN 0, own
admin queue, CC.EN 1: [SP11-NVME-WINDOW.md](SP11-NVME-WINDOW.md) rows 9 to 11, D8, D11; the producer of the SP11
target and record and the monitor's entry are UNIMPLEMENTED, rows 16 and 17). The SP11 entry also re-proves the
endpoint (`nvmeh_sp11_prove_endpoint`): a function that is present, class 0x010802, command bits 0x6 (memory space
and bus master), header type 0 and BAR0 equal to the monitor's `bar`.
T06 therefore tells the takeover what it starts from. The readings below are INFERRED and were written before the
run; the run of 2026-11-15 matched the first row (section 13), and no other row has been seen on the unit.

| T06 shows | Reading | For the NVMe host |
| --- | --- | --- |
| **MATCHED on the unit, 2026-11-15 (section 13):** PASS; CC.EN 1, CSTS.RDY 1, AQA, ASQ, ACQ equal to PRE and non-zero | the firmware left its controller running with its own queues (the D8 expectation) | reset first, then adopt: the takeover needs the full quiesce (CC.SHN normal, wait, CC.EN 0); `nvmeh_adopt` as it is would refuse (queues not the monitor's) |
| PASS; CC.EN 0, CSTS.RDY 0 at EL2 while PRE had them 1 | the firmware's ExitBootServices handling shut the controller down | the takeover starts from reset and needs no quiesce wait; adoption still follows q1n1's own queues |
| PASS; AQA, ASQ or ACQ differ from PRE while CC.EN is 1 | something rewrote the queue registers after the firmware's read | the firmware's queues are no longer trustworthy: reset before use, and find out what wrote them first |
| `EP CMD` without 0x6 | memory or bus-master decode is off at EL2 | `nvmeh_sp11_prove_endpoint` would refuse (`DEVICE_DISABLED`); q1n1 must enable them after proving the function |
| FAIL (ids, class, BAR0, CAP or VS) | the topology at EL2 is not the one the firmware used, or the reads are not the controller's | no NVMe work; the target (segment, ECAM, BDF, BAR) must be re-derived; the monitor's endpoint proof would refuse on `BAR`, `CLASS` or `NO_DEVICE` |
| UNKNOWN, a read faulted | the NVMe's root complex or its link is not reachable at EL2 as the firmware left it | the NVMe is out of reach until q1n1 brings that root up (clock, PHY, link): UNIMPLEMENTED; D15 is then answered "link not up at EL2" |
| a hang on the footer's window | as above, without the guard's help | same, and T06 can not report; the footer names the address |
| NOT-RUN | the firmware's PCI I/O showed no usable NVMe, or the two sources disagree | D2 to D4 stay UNKNOWN; a different source for the segment is needed |

## 9. Remaining hazards

Written before the run; each bullet now also says what the run of 2026-11-15 (one unit, one boot; section 13)
answered.

* **The collection before ExitBootServices** reads functions the firmware itself enumerated, through the firmware's
  own driver, so a stall there is not expected (INFERRED, UNTESTED on the unit). If it happened the console would
  show `SP11X2 BEGIN ...` but no `SP11X2 PCIIO STATE=...` line (it is printed when the collection returns), and
  the image would never reach the bounce. **Answered, once:** it did not stall. The image reached the bounce, T06
  printed `FW NVME FUNCTIONS=1` and the firmware's own `PRE` values, and the run directory holds `pciio.txt` with
  `state=OK` (section 13). The console line itself was not photographed.
* **The NVMe's own root complex may still not answer at EL2.** Not expected to hang if its link is merely down
  (an all-ones read or a guarded fault), but that is UNTESTED on the unit. The footer names the window and the
  8 s pause protects the page, not the machine. **Answered, once:** the root complex answered. The root port and
  the endpoint were read, the link is Gen4 x4 with `DLLLA=1`, and there was no all-ones read, no fault and no hang.
  The link-down branch was not exercised.
* Why segment 3 stalled is UNKNOWN. If its cause is not specific to segments the firmware left unused,
  segment 6 can stall too. **Still open:** segment 6 did not stall in this boot, and segment 3 was not read (by
  design), so why segment 3 stalled is still UNKNOWN. `pciio.txt` adds that the firmware located no function behind
  segment 3 (nor behind 0 to 2, 5 or 7), which fits a root complex the firmware never brought up (INFERRED, untested).
* `_UID` = `_SEG` is INFERRED; the run-time cross-check turns a wrong guess into NOT-RUN with nothing read.
  **Answered, once:** the cross-check passed (root UID 6, segment 6, exactly one MCFG entry, start bus 0).
* Whether the memory map lists the segment-6 windows as MMIO is UNKNOWN. Under the default policy an unlisted window is
  read; a window the map lists as RAM, firmware or reserved is refused (`MAP ... REFUSED=<k>`). **Answered, once:**

## 11. Where the brief and the code differ

* **2^36.** The brief first said to validate windows "below 2^36". `env.h` has `TESTS_PA_LIMIT` as `1ull << 52`
  and no 2^36 rule; the amendment says to keep the code's policy and add none, and none was added. An earlier note
  of the v2 run says segment 2 (base 0x6000000000, above 2^36) was "refused by T06"; the code at the v2 commit has
  no such refusal, so whether v2 read segment 2 before it reached segment 3 is UNKNOWN. The likely origin of the
  remark (INFERRED) is the monitor's `NVMEH_SP11_IPA_LIMIT` in `compat/nvme-host.h`, which bounds the monitor's
  stage-2 map and the target it will accept, not what T06 may read.
* Both PNP0A08 and PNP0A03 roots are accepted (QEMU/EDK2's roots are PciRoot).
* For a header type 1 function only BAR0 and BAR1 (and 0x18) are read: offsets 0x18 to 0x24 are not BARs there.
* `LocateHandleBuffer` is called through a locally typed cast; the shared `efi_types.h` slot stays untyped.
* Verdicts go beyond the literal brief: UNKNOWN for a refused window, an incomplete record or an unchecked firmware
  NVMe (`suite.h`: a test that cannot justify an address says UNKNOWN and why); the EL2 registers are read only when
  the view matches the firmware's (stricter than the brief).
* `pciio.txt` records state names (`NO PROTOCOL` ...) and `nvme=0` rather than a literal `NONE`.
* The footer reads `PHOTO NOW: T06 ECAM <addr> IN 8 S` (37 columns), not `T06 PHOTOGRAPH NOW: READING ECAM IN 8 S`
  (the footer is 38 columns and the address has to be named).
* Tests that pinned the dump file count (QEMU `FILES=4`) or the stick call of the not-at-EL2 path (0 files) now
  pin 5 and 1; the pins were changed, not weakened.
* The old `NVME CAP=` row is replaced by the PRE/EL2 rows.
